# Parallel builds — per-request concurrent dev runs (design)

Status: **SHIPPED — MR1 (ledger + chokepoint), MR2 (run-scoped plumbing), MR3 (parallel ON, admin-gated; instance default stays 1) and MR4 (stacked per-run console UX: dev_runs[] on the detail payload, sibling RunConsoles with per-run stop, buildingIds rail pulses, aggregate now-copy) all shipped; the hub gains the parallel surface when its pinned SHARED_UI_REF is bumped past MR4 (additive props - the pinned console keeps working unchanged until then)**. MR3 deviations from this design: the devmerge lock is deferred (demolock already serializes deploys, verifies are per-run sandboxes, and an interleaved merge falls into the conflict-park path); dev_runs[] serialization ships with MR4. Implementation note: per-run stop markers, the row-driven reaper, and per-run verify naming moved from MR2 to MR3 (they only matter once siblings exist; at limit 1 the project-scoped forms are exactly equivalent), and the billing watermark ships as additive bookkeeping next to read-then-unlink. Produced 2026-08-07 by a multi-agent design review (5 subsystem maps → 3 independent designs → 2-judge panel → 3 adversarial verification passes, 29 breakages found and folded back in). This document is the implementation contract for the MR train in §9; PROMPT.md/API_CONTRACT.md/CLAUDE.md are updated per-MR as behavior actually lands (docs describe current state only).

## 1. Goal and non-goals

Goal: N concurrent dev runs per project — one per request, each with its own live console, branch, feed, billing, stop/resume, and park semantics — behind a per-project entitlement that defaults to today's serialized behavior.

Non-goals: cross-run git conflict resolution (the second merge after a sibling lands may conflict; it parks failed+resumable and the resume re-anchors on the new base — by design), parallel demo deploys (the demo stays a per-project singleton), multi-node runner scheduling (the K8s RWO workspaces PVC keeps dev Jobs pinned; scaling out is a separate program).

## 2. Gating — the licensing-ready entitlement

The entitlement is a concurrency **limit**, never a boolean: `Project.dev_parallel_limit` (nullable int, null = inherit), instance envs `DEV_PARALLEL_RUNS_DEFAULT` (=1) and `DEV_PARALLEL_RUNS_MAX` (=3, hard ceiling).

One chokepoint resolves it: `services/dev_concurrency.py::effective_parallel_limit(db, project) = max(1, min(project.dev_parallel_limit or default, max, _entitlement_limit(db, project.org) or ∞))`. `_entitlement_limit` returns None today and is the **only** place the future license/plan layer plugs in — no dispatch site ever changes for licensing (precedent: per-project `dev_max_iterations` resolved at dispatch).

`dev_concurrency.acquire_slot(db, project, request)` is the **sole creator of DevRun rows**: SELECT..FOR UPDATE on the project row, count active runs, refuse at the limit with today's exact copy, refuse a second active run for the same request (partial unique index as the DB backstop), then create the row and dispatch. Wallet-aware admission: `balance >= (active_runs + 1) × DEV_RUN_CREDIT_FLOOR` shrinks the N−1-dispatch overdraft window.

Every `run_development` sender goes through `acquire_slot` — the verified-complete list: `handle_request`, `project_actions.retry_build` (SPA + hub actions + MCP wrap it), the classifier's resume and confirm branches (main **and** thread), `_sweep_auto_dev_project`, **plus the three sites the first draft missed**: the admin status route (`api/admin.py` set-status kick), `maybe_start_development` (payment_due auto-advance), and the plan-gate approve/feedback re-dispatches (which re-validate their slot). `acquire_slot` is implemented once, sync; async API contexts call it via `run_in_threadpool` (knowledge.py precedent) so the chokepoint cannot fork.

Admin surface: the limit in `AdminProjectControls` (1..max, null = default), validated server-side. `project_out` serializes **both** the raw override and the resolved effective value (`dev_parallel_limit`, `dev_parallel_effective`) so the admin UI edits the raw value while the SPA/hub adapt behavior on the effective one.

## 3. Data model — DevRun rows under mirrored scalars

New table `dev_run`: id, project_id FK, request_id FK **nullable** (null = legacy pre-threads run narrating to main, mirroring `_dev_thread`'s existing fallback), state (`queued|running|awaiting_merge|deploying|failed|done|idle`), started_at, workspace_dir, branch, pr_number/pr_url, run_log/run_error, security_review/acceptance/harness_version snapshots, tokens_consumed/cost_credits, billed_through (billing watermark), predecessor_id (run chains). Partial unique index: one active run per request across `running|awaiting_merge|deploying|queued`.

`queued` exists because dispatch is accepted before a Celery slot frees up: it counts toward the limit but is excluded from the in-flight reaper set (a longer queue-reap bound covers it); `run_development` flips queued→running and stamps started_at. `idle` (plan-pass terminal) is in the enum and excluded from the active count — the plan run's row must reach a terminal state.

The existing `Project.dev_*` scalars are **kept as a mirror of the primary run** (most-recently-started active run, sticky until it finishes). The mirror is recomputed from the DevRun table only under the same FOR UPDATE lock `acquire_slot` takes — `_save_run`'s current unlocked read-compare-write cannot arbitrate siblings. At effective limit 1 the sole run is the mirror: byte-identical behavior, and a regression test proves `acquire_slot` at limit 1 refuses in exactly today's three states with today's copy.

The run pipeline's identity reads/writes move **entirely** onto the row: `_ensure_dev_branch`/`_project_branch`/`_reset_stale_branch`, PR pointers, `_dev_thread` (thread = `request:<run.request_id>`), security review, acceptance, steering cutoffs. `Project.dev_request_id`/`dev_branch`/`dev_pr_*` become mirror-only outputs — the verifiers showed they are a sixth shared mutable resource if any consumer keeps reading them mid-run. `DevRunRecord` gains a `dev_run_id` FK so harness eval reads per-run truth.

Migration is additive (table + two nullable columns). In-flight bridge: `run_development(run_id=None)` **creates-or-adopts** a row idempotently under the partial index with a claim CAS (never blind-resolves), covering Celery messages queued across the deploy; the deploy runbook drains the dev queue first.

## 4. Execution — workspaces, runner, deployer

Per-run workspaces live **outside** the project checkout: `<workspaces>/devruns/<project_id>/<run_id>` (precedent: `/workspaces/.kb-git`, a subtree the demo/verify/SBOM sandboxes never mount). Nesting `runs/` inside `Project.workspace_path` is rejected — it would ride into every `sync_workspace` demo copy, boot verify, and SBOM scan, and a mode flip mid-run would give a legacy runner a workspace containing live sibling checkouts. Legacy mode (limit 1) keeps `Project.workspace_path` exactly as today; the `workspace_dir` column being empty is the only branch point. Workspace-mode exclusivity (`_mode_conflicts`) keeps the two modes off one working tree, with one exemption: a legacy row parked in `awaiting_merge` does not block parallel admission (its branch and PR are pushed, no runner is executing, and `_refresh_root_workspace` rebuilds the canonical checkout fail-loud before its merge deploys), so an admin-raised limit takes effect instead of dead-lettering behind a human merge; a §revise chain continuing such a superseded legacy row converts to a fresh parallel dir at limit > 1 (the runner entrypoint continues from origin/<branch>), while failed legacy chains - unpushed work living in the canonical checkout - stay legacy-mode and keep waiting for every parallel sibling.

Seeding: hardlinked local `git clone` from the canonical checkout (cheap, and `entrypoint.sh` re-points origin and fetches anyway — zero runner-image changes). A retry/boot-fix/resume **inherits the predecessor run's workspace_dir and branch** (new row, same dir — run chains), preserving the local-unpushed-branch continuation guarantee per run. Retention: parallel run dirs pruned to `DEV_RUN_DIR_RETENTION` per project, failed-resumable dirs exempt (Programs parity). Dispatch asserts no two in-flight rows share a workspace dir — the leak-scan fail-closed contract ("missing staged input = tampered") is load-bearing on that exclusivity.

Deployer: `DevRunIn` gains `run_dir` (validated `_DEV_RUN_DIR_RE` + realpath containment, Programs discipline) and `run_name` (container/Job/Secret naming `dev-<pid>-<run8>`), `/dev/stop` gains `run_name`, `/demos/verify` gets a per-run **container** name but keeps the per-project `-data` cache volume (safe: `verifylock` serializes verifies per project), `k8s.py` mirrors job/Secret/PVC-subPath **and threads run_dir into `_job_logs`** (its deadline-kill fallback reads the workspace log path — exactly the timeout case). Empty defaults keep every field old-worker/new-deployer compatible. The dispatch-time kill-leftover (`docker rm -f` / Job delete) becomes run-scoped so a sibling dispatch can never kill a live runner. Defense in depth: a deployer-global `DEV_MAX_CONCURRENT_RUNS` backstop (429 → the worker parks the dispatch queued).

Branch uniqueness: `_ensure_dev_branch` rejects a candidate equal to any non-finished sibling's branch and suffixes `-<req8>` deterministically.

Capacity: `run_development` stays synchronous and non-acks_late, so a dedicated `dev` Celery queue sized to the concurrency budget keeps N runs from starving emails/sweeps/beat recovery.

## 5. Money and safety

Billing: per-run `usage.json` under the run's workspace, and a `billed_through` watermark on the row instead of bare read-then-unlink (the boot-gate wait made unlink-based exactly-once reaper-fragile). Attribution always `db.get(Request, run.request_id)` — never the mutable project pointer. **All three** wallet writers (`record_usage`, `record_project_usage`, `record_org_usage`) plus the service-layer debits become atomic `UPDATE organization SET credit_balance = credit_balance - :x` — the design converts the whole class, not one instance.

Leak scan and feed redaction: every `.openvisor` input/output path (`_prepare_runner_inputs`, `leak_secret_env.txt`/`leak_kb.json`, `devfeed._guards`, `_agent_pr_body`, `_read_plan`, reaper usage recovery) re-roots through one `_run_ws(project, run)` helper — a missed re-root silently redacts run A's feed with run B's fingerprints, so the helper is the only sanctioned path join and a test greps for direct `Path(project.workspace_path)` joins in the run pipeline.

Stop/reaper: stop and ownerless-stop reap query DevRun rows by state, never the mirror (the mirror can legitimately show a non-running primary while a sibling runs). Per-run stop markers `devstop:<run_id>`; the legacy no-run stop resolves any running run and 409s only when none exist. `started_at` is re-stamped when entering (and heartbeated while waiting on) `verifylock`, so boot-gate queueing can never present as a reapable orphan.

## 6. Merge and demo tail

The demo stays a singleton; the tail serializes per project under a `devmerge:<project_id>` redis lock (two `_remote_auto_merge` loops' fix dispatches and re-boot-checks never interleave; demolock already coalesces the deploys themselves). Before any demo (re)deploy, `_refresh_root_workspace` fetches + hard-resets the canonical checkout to the merged base — clone-if-absent (a project that went parallel pre-MVP has no root checkout yet), fail-loud (park the deploy rather than ship a stale tree), idempotent when two merges land in one sweep tick.

Run finalization keys on the **owning run**: `demo_start` receives the run id and finalizes that row (and its request) only when it owns a `deploying` DevRun — never on the mirror scalar (manual demo starts pass no run and finalize nothing). Platform-GitLab merge conflicts after a sibling's squash merge map to the same failed+resumable park as the customer path ("a sibling change landed first — Resume re-anchors on the new base"), not `awaiting_admin`.

Project-status rollup in parallel mode: the project stays `development` while any run is active; it moves to `awaiting_customer` only when every active run waits on the customer, and a failure park transitions the project only when no sibling is live. Chat classifier gates count active DevRun rows, not `CHAT_INFLIGHT_STATES` on the mirror - and gate only the dispatching intents (resume/confirm/revise): new_request and clarify file a proposal / ask their one question without a free slot, so an ask stated mid-run is filed, never swallowed into a work answer. Steering: each resume takes its own run-chain cutoff and its request thread; a main-thread "@agent do X" is claimed by at most one resume (claim marker), never folded into every sibling.

## 7. UX

At limit 1 or a single active run: exactly today's UI off the mirror — zero visual change. With siblings: the overview Development area stacks one console per active run ordered by `started_at` — primary expanded, siblings as collapsed headers (request title, state, elapsed, tokens) — each with its own `?run_id=` feed poll, counters, branch/PR chips from the row, and Stop/Resume scoped to its run (`stop-build?run_id=`; `retry-build {run_id}`, which the request-thread history console also offers on a failed row, gated per row by its `can_resume`). `GET /projects/{id}/dev-activity?run_id=` (absent = the primary run, resolved server-side via `dev_concurrency.primary_run` - the mirror's most-recently-started active row, sticky when finished - so the mirror-driven console is correct even when the primary is parallel-mode); WS `dev` events gain additive `run_id`/`request_id` keys. ThreadRail keeps `buildingId` (hub pin compat) and gains additive `buildingIds` pulsing every building chip. The request-view console (shipped in !225) becomes a lookup into the per-request run map — the primary parallel surface, already laid out. `now.ts` gains aggregate copy ("2 builds running · 1 pull request waiting") with singular fallback.

## 8. Back-compat contract

No `Project.dev_*` column is dropped or repurposed; `project_out` keeps every existing field with mirror semantics (sticky primary), and adds `dev_parallel_limit`, `dev_parallel_effective`, and `dev_runs[]`. The pinned-SHARED_UI_REF hub console keeps working unchanged at any limit; hub actions inherit the gate through `project_actions`. Legacy projects (no MVP Request row) run with `request_id NULL` and main-thread narration, exactly as `_dev_thread` falls back today.

## 9. MR train

1. **MR1 — ledger + chokepoint (dark)**: `dev_run` table + partial index + `dev_parallel_limit` + migration; `dev_concurrency.py` (`effective_parallel_limit`, `_entitlement_limit` hook, `acquire_slot` with wallet floor); every dispatch sender routed through the gate; queued state; run_id=None create-or-adopt bridge; limit hard-wired 1 — provable-identity tests ship here.
2. **MR2 — run-scoped plumbing (defaults = legacy)**: deployer `run_dir`/`run_name` + run-scoped stop + verify naming + k8s twins incl. `_job_logs`; `_run_ws` re-root of the whole run pipeline + the no-direct-join test; per-run feed paths + `?run_id=`; per-run billing watermark + atomic wallet UPDATEs (all writers); per-run stop markers + reaper by rows.
3. **MR3 — parallel ON (admin-gated)**: `acquire_slot` honors the limit; devruns workspace seeding + chains + retention; branch-uniqueness; `devmerge` lock + `_refresh_root_workspace` + run-keyed finalization + platform conflict-park parity; status rollup + classifier gates; admin card control; `dev` Celery queue + deployer backstop.
4. **MR4 — parallel UX + hub**: stacked/collapsed consoles, `dev_runs[]`/`buildingIds`, request-view per-run consoles, aggregate now-copy; hub SHARED_UI_REF bump.

## 10. Accepted risks

Git-conflict-by-design between sibling merges (park + re-anchor, surfaced honestly in the thread); dual legacy/parallel path until a post-MR4 consolidation (single `workspace_dir` branch point, both paths under the same tests); single-node runner pressure on K8s (`DEV_PARALLEL_RUNS_MAX` + deployer backstop are the brakes); a bounded overdraft window of at most the credit floor × active runs.
