# Code map - Openvisor

The detailed tour of every subsystem, split out of [CLAUDE.md](../CLAUDE.md) so
that file stays a working brief rather than a reference manual. CLAUDE.md keeps
the rules, the workflow and a one-line index of these paths; this file is where
the detail lives.

`§N` references point at the platform's internal product spec, which is not
shipped in this repository - treat them as stable anchors, not links.

Same doc rule as everywhere else: a change that alters behavior described here
updates this file in the SAME merge request, and it describes the current state
only - never narrates removed behavior.

## Subsystems, path by path

- `backend/app/services/statuses.py` + `lifecycle.py` - the §8 status machine. `can_transition()` is the single source of truth; `transition_async` (API) and `transition_sync` (Celery) apply side effects: `status_change` row, system chat message, WS event, notification emails. Admin can move anywhere; customer/agent can always push to `awaiting_admin`; the agent can never approve, price, or advance.
- `backend/app/services/project_actions.py` - the shared customer-action service layer (§hub pass-through P0): `evaluate`/`submit`/`require_review`/`retry_build`/`stop_build`/`approve_delivery`/`validate_request`+`cancel_request` (§requests: the human closes an AI-handled request by hand - validate = done with its awaiting_merge run closed and the mirror repointed, cancel = rejected with the run parked failed and the work unit ended sweep-style, pointers cleared, console settled idle; neither ever touches a live build; §12 one-click confirm: `start_request` on a still-`proposed` request posts the canned "Go ahead" reply + the agent's "On it" ack to main, and `cancel_request` on one posts "Not now" + the drop ack - the deterministic twins of the chat confirm verdict, freezing the proposal ack's ✓/✗ panel (shared-ui `ConfirmPrompt`, `Message.meta {kind:"confirm_request"}`) whichever surface acted)/`post_chat_message` (+ `valid_thread`) hold every action's guards + side effects keyed on `(db, project, actor)` - never on a session User - raising `ActionError(status, detail)`. §threads Request #0: `create_mvp_request` (called inside both project-create transactions for ai-kind) births the initial build as a `type='mvp'` Request (title "Initial build", thread seeded with the description) so `_dev_thread` narrates MVP runs into it (fallback main for pre-threads projects), `_bill_dev_run` attributes MVP usage to it, dispatch marks it `in_progress`, and a TERMINAL project transition closes it - owned by `services/lifecycle` (not `approve_delivery`) so every route agrees: `finished` → `done` (a delivery the customer accepted), `canceled` → `rejected` (nothing was delivered, and the request must not claim otherwise), already-closed rows untouched. Owning it in the one chokepoint is what stops an admin status change - or a project with no MVP phase, where `validate_request` refuses mvp rows and `approve_delivery` waits on a demo that never comes - leaving Request #0 stranded `in_progress` forever; it is server-side only (client schemas' type Literal), `start_request` 409s it, `handle_request` ignores it, and the plan-gate approval QuestionPrompt stays pinned to main (orchestrator decisions in main, narration in threads). The SPA routes in `api/projects.py`/`api/chat.py` are thin wrappers (role → actor, HTTP mapping, serialization), and the forthcoming hub pass-through routes will wrap the SAME functions, so the two surfaces can't drift. Each action commits (the service is the transaction boundary). Add new customer actions here first, then wrap.
- `backend/app/workers/tasks.py` - all Celery tasks: `evaluate_project` (moderation → feasibility → estimate), `provision_project` (GitLab project/deploy-key over HTTPS + best-effort customer user, tolerant of GitLab being down), `run_development` (assembles the OpenHands task - system prompt + standing-rules digests + task-matched procedures (§KB tiers, injected above the customer-data boundary on every pass incl. plan/consult, procedures keyed on the scoped request / fix / steering text; FULL texts join the leak-scan fingerprints) + project context + RAG + Memory - writes runner inputs and dispatches the sandboxed dev job when `OPENHANDS_ENABLED=1`, else a local scaffold fallback; provider-aware via `_dev_target` which resolves a BOUND run's pinned repo first (§repo binding: `_run_repo_target` - the `repo_id` stamp, else chain-PR-URL recovery for pre-binding rows matched against connected repos / the platform web URL - so a chain, the merge sweep and every publish step stay on THEIR repo whatever the panel's radio says today) and only live-resolves the project's push repo for unpinned contexts (§multi-repo) - a customer GitHub repo → GitHub PR path, a customer GitLab repo → customer-GitLab MR path (both share `_run_development_customer` + `_remote_auto_merge` via a provider `ops` adapter), an `other` host → branch-push path, else the platform GitLab auto-merge-on-green-CI path; persists `dev_run_state/_log/_error/_pr_*` for the build panel; §14 don't-lose-landed-work: a runner that exits non-zero - or exits NO_CHANGES - AFTER its work landed adopts the change instead of parking failed (`_adopt_landed_work`, three probes, strongest first: `_adopt_merged_change` - a change pointer the PLATFORM itself stamped on the run's chain (run rows → project mirror → request history, each URL-matched against the resolved target so a re-pinned chain never resolves a foreign repo's number) is already MERGED, and the park proceeds like the merge sweep's merged branch instead - `_proceed_merged` finalizes a pr-deliverable request, else deploys the demo, so a resume of an already-delivered request that correctly produces nothing ends DELIVERED, not "no changes" (also probed on the NO_CHANGES park, ahead of probe 2); `_adopt_bound_branch` - the run's branch on the BOUND repo with an open PR/MR pointing at it; else `_adopt_declared_change` - an open PR/MR the run's own pr.md DECLARES on ANOTHER connected repo (a full URL, a backticked head branch, or an explicit "PR #N"/"MR !N") - the ref must resolve on a ProjectRepo row and the change must be created OR updated in this run's window, so a summary merely citing an old PR never adopts; open-change adoption stamps run.repo_id + the PR's head branch so the branch chip links to the repo the change lives on and the merge sweep polls the right repo): the pushed diff's added lines are leak-scanned worker-side first (a hit fails closed to awaiting_admin with a PUBLISHED-change alert - the runner's own pre-publish scan doesn't cover a push the agent made from its shell), a clean change parks awaiting_merge with the PR pointers set for the merge sweep, and adopted work is NEVER auto-merged - an errored session always gets a human review; Reached three ways: the `answer` verdict, an `@agent`/`@ai` mention that would otherwise be silent (`mentions_agent` - the classifier still runs and action verdicts still win, but an outage/none/unavailable-action falls back to answering), and a question asked mid-run (`actions_allowed` gates only the ACTION branches now - answering reads, so it is allowed while `dev_run_state` is running/deploying/awaiting_merge). - `backend/app/services/github.py` - GitHub provider (mirror of `gitlab.py`) for customer-owned repos: `is_github`/`parse_repo`, `ensure_base_branch` (seeds `main` on an empty repo so a PR has a base), `open_pr`/`find_open_pr`/`get_pr`, `check_repo_access` (auth check gating auto-merge). Deploy keys push the branch; PR creation needs `GITHUB_TOKEN` (deploy keys can't open PRs). `gitlab.py` mirrors this for a CUSTOMER GitLab host (the `customer_*` fns + `is_gitlab`/`parse_repo_path`/`check_repo_access`, all taking base_url + a per-project `GITLAB_TOKEN`) separately from the platform-GitLab functions. An instance knows its OWN GitLab by two hostnames that need not match - `GITLAB_URL`'s (what `/api/v4` answers on) and the optional `GITLAB_SSH_HOST` (what git dials, e.g. `git.example.com:10022`) - and `is_platform_host` is the single place that decides whether a remote is ours (§ssh remotes). It makes `is_gitlab`/`detect_provider` recognise a repo cloned over the SSH name (else `other`: no issue watching, no MR integration), points `customer_base_url` at `GITLAB_URL` (deriving `https://<ssh-host>` reaches a host that need not serve the API and on a tailnet is not routable from the api/worker pods at all), and gates the `settings.gitlab_token` fallback in `_project_repo_token(db, project, provider, uri)` - that `uri` is load-bearing SECURITY, since the platform credential may fall back only for a host we own and a caller naming no repo gets no fallback. `services/repos.py` is the small policy layer: `detect_provider(url)` (github|gitlab|other from the host - `other` is buildable but never auto-mergeable), `token_key`, `check_auth` (dispatches the per-provider auth call), and `git_identity(project)` (§git identity) - the ONE resolution point for what the agent's commits are authored as: the project's `git_author_name`/`git_author_email` override, else the brand-derived default (`<BRAND_NAME> agent` / `agent@<DEPLOY_DOMAIN>`). It is edited on the project's Git-identity card (`PATCH /projects/{id}`, `""` = reset to default, line breaks and angle brackets refused because the value lands in `git config`) and threaded to the sandbox as `GIT_USER_NAME`/`GIT_USER_EMAIL` (`_dispatch_runner` → `/dev/run` → `entrypoint.sh`), so the payload, the UI hint and the runner can never disagree.. Multi-repo (§): every connected repo is a **working repository** - the runner shallow-clones each non-push repo read-only into `.openvisor/context/<name>` (worker writes `context_repos.txt`, task lists the paths) - and a project builds into its **push repo** - a connected repo (`ProjectRepo`, `provider`/`is_push_target`/`auto_merge`/`squash_on_merge`/`summarize_to_issue`) marked `is_push_target`, else the platform GitLab repo; the repos API (`api/projects.py`, `POST/PATCH/DELETE /projects/{id}/repos*` + `verify-auth`) enforces exactly-one push target and gates enabling `auto_merge` on a passing server-side auth check. Platform-initiated merges squash the agent's PR/MR into one commit by default (`squash_on_merge`, a per-push-repo checkbox; the platform GitLab repo always squashes; a repo whose settings forbid squashing falls back to a plain merge instead of parking).
- `runner/` - the OpenHands dev runner image (one sandboxed container per build). `run_dev.py` drives the OpenHands SDK v1 (`get_default_agent(llm)` + `Conversation(workspace="/workspace", max_iteration_per_run=LLM_MAX_ITERATIONS)` - the cap is a constructor arg and the SDK swallows unknown kwargs, so the driver verifies it landed and warns when an SDK bump silently drops it; the preset condenser is swapped for a `RetryingCondenser` because condensation is the one chat-completions call in a build - agent steps ride the Responses API on gpt-5-family models - and litellm never retries 4xx, so a transient provider rejection there used to kill whole runs); `entrypoint.sh` wires the MCP config + per-project deploy key, starts the §dev-docker inner dockerd when `DEV_DOCKER=1` (best-effort - the image ships docker CLI + compose plugin; the deployer only sets the flag when `DEV_SANDBOX_DOCKER=1` granted the runtime) and pushes the agent branch (fetch is `--prune`d; a branch that exists only LOCALLY with unpushed commits containing the base is continued, never re-anchored - a crash/timeout/gate park after commit must not orphan the work; just before the push, the UNPUSHED commit range is msg-filtered to drop tool-attribution trailers (Co-authored-by: openhands / Signed-off-by - the agent's commit tooling appends them below any task instruction's reach; the commit-message twin of the worker's `_strip_commit_trailers`, bounded to `$SCRUB_BASE..HEAD` so commits already on the remote and base history are never rewritten); a rejected force-with-lease push gets one ref-refresh retry; a push that still fails exits 4 with a `PUSH_FAILED` sentinel, which the worker's `_push_failed`/`_fail_push` park as a failed+resumable run instead of publishing/merging stale state; the **§publish gate** exits 5 with `NO_CHANGES_TO_PUBLISH` when the session produced nothing - no staged change beyond the runner's own `.gitignore` line, no real agent `.gitignore` edit, and no committed branch content vs the base - so a capped/errored run can never ship a plumbing-only commit as a PR: `_no_changes`/`_fail_no_changes` park it with a nudge toward the chat steering channel - and when the session ended at its iteration cap the copy SAYS so: the driver persists `.openvisor/exit_reason.json` {reason: max_iterations, limit} off the SDK's `MaxIterationsReached` event (read-and-unlink, error.json parity), the live feed line becomes "Agent hit its iteration cap", and the park message/run error name the cap + Resume instead of the misleading generic "no changes"). `live_events.py` is the §14.8 live build feed: a Conversation callback (TypeError-fallback if the SDK drops the kwarg) appends sanitized event summaries to `.openvisor/events.jsonl` - only summaries composed there, never raw model/tool output, task text, or command output - and throttle-snapshots token usage to `.openvisor/progress.json` (display only; `usage.json` stays the billing artifact); `entrypoint.sh` adds fixed phase markers (`emit_event`, no dynamic interpolation) and runs the driver with `python -u` so `run.log` grows live. Built with `uv` (pip can't resolve openhands-ai's opentelemetry graph). Launched by the deployer `/dev/run` endpoint, which bind-mounts the project's workspace subdir from the `openvisor_workspaces` volume. The LLM model is prefixed `openai/` in the driver so any OpenAI-compatible endpoint routes through LiteLLM. `leak_scan.py` is the pre-publish hard boundary behind the dev prompt's confidentiality rules (development_system.md §9-11; the connected-MCP-KB rule 12 is prompt-only, not scanner-backed): `entrypoint.sh` runs it after `git add -A` and before commit/push; it refuses (exit non-zero → sentinel `LEAK_SCAN_BLOCKED`, no push) any staged `.openvisor/` path (runner-internal inputs incl. the deploy key - the entrypoint appends `.openvisor/` to the repo's `.gitignore` post-checkout and `git rm --cached`s it after `add -A`, so a survivor means that plumbing failed), any staged file matching a PEM private-key header (`PRIVATE_KEY_RE`, value-independent), and any that contains a secret value **or its base64/hex encoding** (`_secret_variants`: secret Memory values looked up by name from `.openvisor/leak_secret_env.txt`, `LLM_API_KEY`, the deploy-key body, the connected-KB keys) or verbatim knowledge-base text (worker-computed fingerprints in `.openvisor/leak_kb.json`, with prompt-mandated templates/customer-supplied text filtered out to avoid false positives). The same checks run over three surfaces via `_scan_blob`: the staged files, the **commit messages** of this run's new commits, and the **added lines** of those commits (range `HEAD --not --remotes`, guarded on remote refs existing) - so a secret committed then reverted from the working tree, or hidden in a commit message, is caught too, not just the final snapshot. The worker's `_leak_blocked`/`_fail_leak` fail closed to `awaiting_admin` and email the admin; `LEAK_SCAN_KB=0` disables only the KB half; it fails open on an internal scanner error by default (defence-in-depth, not the sole control - the prompt rules are primary), `LEAK_SCAN_FAIL_CLOSED=1` flips that to block-on-scanner-error; a missing `leak_secret_env.txt`/`leak_kb.json` (the worker writes both on every dispatch, empty included - absence means the agent deleted the `.openvisor/` inputs mid-run, e.g. `git clean -fdx`) counts as an internal scanner error, never a silent scan with a reduced refuse-set.
- `backend/app/services/devfeed.py` + `GET /api/projects/{id}/dev-activity?offset=` (`api/projects.py`) - the §14.8 live build console. Serves `events.jsonl` + `progress.json` off the workspaces volume by offset-polling (Programs-log parity, threadpool reads, only complete JSONL lines consumed; a missing/replaced file hands back `reset`/a smaller `next_offset` so the SPA restarts its buffer), with a second defensive pass per chunk: platform-secret values redacted (`leakscan.platform_secret_values` + the project deploy key), and any line carrying PEM material or a verbatim KB span (the run's `leak_kb.json` fingerprints) withheld. `read_progress` adds a display-only credit estimate via `pricing.cost_credits` (billing untouched). MCP tool calls are titled with the tool's NAME (from the event's `tool_name`; the args dict never reaches the feed). ## Chat images (§chat images)

Images pasted, dropped or picked into a chat thread, sent to the model as OpenAI content parts.

- **§chat images → sandbox**: the screenshots also reach the dev agent. `workers/tasks.py::_stage_chat_images` (called per dispatch from `_prepare_runner_inputs`) stages the conversation's images under `.openvisor/images/` with a manifest (`images.json`), vision-gated at dispatch time (the model can change after upload); thread scope mirrors §steering scope (a scoped request stages its OWN thread, MVP/unscoped adds main) and a chained run stages only images its predecessor never saw. The task gains a "Conversation screenshots" block (customer-supplied data, rule 11), and the runner (`run_dev.py::_with_images`) attaches the staged files as inline data-URI `ImageContent` parts on its first message - fresh runs on the task, resumed runs on the steering note - falling back to plain text on any SDK refusal so an image can never fail a build.

- **The capability question has no standard answer.** `/models` returns ids, never capabilities, so `ModelEndpoint.supports_images` is a stored TRI-STATE: `null` (nobody checked), `true`, `false`. The endpoint Test probe IS the discovery - it posts a 1x1 PNG as an `image_url` part and reads the answer; a 400 naming image/vision/content-type is a `false`, anything else (rate limit, outage) leaves the stored verdict alone so a blip can't record a false negative. `supports_images_source` is `probe` or `admin`, and an admin declaration outranks a probe and survives later tests. The instance-default model has no endpoint row, so it carries the same declaration as an `AppSetting` (`default_model_supports_images`).
- **One resolver, two twins.** `services/vision.py` answers `{enabled, reason, model}` in the same order as `_project_model_config` (saved endpoint → legacy inline → instance default), async for the API and sync for the workers, so the chat box and the worker can never disagree. `reason` is the tooltip on the disabled attach button and distinguishes "hasn't been checked" from "can't read images".
- **Storage and claiming.** `ChatImage` rows hold the bytes in-DB (like `ProjectFile`), immutable like the messages they belong to. Upload (`POST /projects/{id}/chat-images`) is gated on the verdict server-side and sniffs the MAGIC BYTES rather than trusting the client's content-type; the message then claims ids via `image_ids`, and `link_to_message` only claims rows that are unlinked, in this project, by the same author - so a message can never adopt someone else's image and an id can never move between messages. The claimed set is recorded on `Message.meta.images` so any reader renders them without a second query.
- **Sending them.** `tasks._message_content` inlines the bytes as data URIs in OpenAI content parts, but only when `vision` says the project's model supports images - a model downgraded after the fact degrades to plain text instead of erroring.

## The dev pipeline end to end (§14)

- OpenHands is real and fully automated (`OPENHANDS_ENABLED=1`): `run_development` checks out the project repo into the workspace, runs the headless SDK build (the runner image - `${COMPOSE_PROJECT_NAME:-openvisor}-runner` for `make dev` via the `build-runner` target; the registry-qualified `.../runner:<tag>` for `make prod`/K8s via `prod-build`, which the compose/chart deployer's `RUNNER_IMAGE` points at) with the §working-method plan gate ahead of it for fresh ai-kind MVP builds (PLAN-ONLY sandbox pass → `.openvisor/plan.md` → chat QuestionPrompt approval, deterministic approve/feedback branch in `classify_chat_message` before the LLM, `Project.dev_plan`/`dev_plan_status`, `DEV_PLAN_CONFIRM`/`DEV_PLAN_MAX_ITERATIONS`), and the runner pushes the run's branch - LLM-named BEFORE anything is committed (prompt #17 `branch_name.md` over the description/policy + scoped request + a targeted KB retrieval for stated naming conventions, honoring any customer branch convention like `f/#-`; sanitized by `naming.sanitize_branch`, persisted as `Project.dev_branch`, kept across resumes, cleared by `handle_request` per new request AND re-derived when the published branch was deleted on the push repo - a closed PR/MR whose branch is gone reads as rejected work, so `_reset_stale_branch` (best-effort, github + customer-gitlab) drops the stale name/PR pointer and the naming prompt re-runs against the current KB; fallback `agent/mvp`). Provider paths (chosen by `_dev_target`'s push repo, §multi-repo): (a) **customer GitHub/GitLab**: the runner pushes over the deploy key with a plain push, the worker opens a PR/MR (per-project `GITHUB_TOKEN`/`GITLAB_TOKEN`; empty repos are seeded with a base `main` first) whose description prefers the agent-authored management-level summary the run wrote to `.openvisor/pr.md` (prompt #5 v10 asks for it; worker-side `_agent_pr_body` redacts platform secrets, drops it wholesale on PEM material, reset per dispatch, template fallback - auto_dev copy never promises a demo redeploy), and with the push repo's `auto_merge` on it runs the §14.7 security-review→merge→fix loop (`_remote_auto_merge`, provider-agnostic via an `ops` adapter), else the customer merges and `dev_pr_sweep` deploys. (b) **other host**: plain branch push, the customer merges, `dev_pr_sweep` detects it over SSH. (c) **platform GitLab**: push options open the MR with NO title option (the entrypoint interpolates no dynamic text, and GitLab applies `merge_request.*` push options to the EXISTING MR on every later push - a fixed title used to retitle agent-authored MRs on each recovery dispatch) which the worker then personalizes - request/project title + the agent's `.openvisor/pr.md` summary via `_personalize_platform_mr` (`gitlab.update_mr`, best-effort, also on reaper recovery; NEVER a downgrade: `_is_generic_mr_title` keeps an agent-authored title, a dispatch that left no pr.md keeps the existing description, and `_strip_commit_trailers` drops Co-authored-by/Signed-off-by noise from pr.md and from whatever description is shown); when the agent committed AND pushed its branch ITSELF the entrypoint's push is an up-to-date no-op and no push option fires, so the worker opens the MR itself (`_open_platform_mr` fallback, personalized copy, loop + reaper recovery; the runner's wrapper commit is best-effort and the push happens regardless) - and auto-merges on green OCPA CI (`merge_when_pipeline_succeeds`, or direct-merge without `.gitlab-ci.yml`). A merge conflict / failed CI / timeout leaves the project in `awaiting_admin` or `awaiting_customer` - on the platform path a timed-out or MR-less run parks failed+resumable exactly like the customer path (never deploying unpublished workspace state or finalizing a request). Every run is bounded by `DEV_RUN_TIMEOUT_MINUTES` (deployer kills an over-running container and reports a timeout - not exit 0) and the agent iteration cap - `DEV_MAX_ITERATIONS_DEFAULT` (instance default, legacy env name `DEV_MAX_ITERATIONS` still read) overridable per project by `Project.dev_max_iterations` (the admin card's Agent-iterations field, 1-500, null = default; resolved at dispatch) - the fail-safes against runaway token spend (keep the DEFAULT tight - raise per project, failure is slow and success is fast); **§investigation runs**: not every task is a diff - "check whether X still holds", "audit Y", "see if Z drifted and open a change if it did" are COMPLETE when nothing is wrong, and the pipeline used to record exactly that as a failed empty build. Prompt #17 step 8 asks the agent to write its findings to `.openvisor/report.md` and finish without committing; `_fail_no_changes` reads that artifact FIRST (`_agent_report`, same channel and the same PEM-drop/secret-redaction pass as `pr.md`) and routes to `_finish_investigation` - the report is posted into the request thread as the answer, the request closes `done` (no PR to wait on: the report IS the delivery) and the run is saved `done`. Guarded to SCOPED requests: an mvp build, or a run with no bound request, still fails on an empty result however eloquently it explains itself, and a run that wrote no report keeps the old failed+resumable park. Letting the AGENT declare the outcome is what keeps the two apart - intent is never guessed up front - and prompt #17 step 9 makes the declaration STRUCTURED (§run outcome): every session ends by writing `.openvisor/outcome.json` `{outcome: changed|no_change_needed|blocked, summary}`, and `_fail_no_changes` cross-checks it against the evidence. `no_change_needed` (or a bare report.md, the v13 back-compat) closes the investigation; `changed` with no publishable diff fails with the DISCREPANCY named ("reported a change but nothing was committed" - the prod run that declared a deliberately-untracked runbook delivered); `blocked` fails with the agent's own blocker as run_error. Missing/malformed declarations degrade to the artifact-only behavior, so a non-compliant agent changes nothing. Otherwise a failed/timed-out run parks the project in `awaiting_customer` with the log kept, and the customer's **Resume development** button (`retry-build`) re-runs it; its sibling **Start fresh** (`retry-build {fresh:true}`, §run chains) DISCARDS the chain instead - every failed run of the request is superseded, the new run is unchained with its own isolated dir in every mode (at limit 1 chaining would reuse the canonical checkout with the discarded work still in it) and naming reserves the request's PRIOR branch names so the fresh branch gets a suffix - because the entrypoint continues `origin/<branch>` and even local unpushed commits, a same-name "fresh" run would silently resurrect the abandoned work. `_save_run`'s shadow-ledger branch backfill applies to CHAINED rows only - stamping the stale scalar onto an unchained row made naming early-return, which is exactly how prod's first Start fresh re-landed on the abandoned branch. The publish gate counts a COMMITTED non-plumbing .gitignore change as a real deliverable (`BRANCH_GITIGNORE_REAL`): excluding .gitignore wholesale from the branch diff told a customer "nothing was committed" over a commit sitting right on the branch, while the pure `+.openvisor/` plumbing line still blocks - folding every customer/consultant message posted in the main thread AND the run's own narration thread (`_dev_thread`) since the previous dispatch into the task as a bounded, author-labeled **steering transcript**, and (§conversation resume) the resumed run REHYDRATES the previous agent session itself: the runner persists the SDK conversation under the workspace's `.openvisor/conversation/` (stable id in `conversation_id`, `delete_on_close=False` - verified against the pinned openhands-ai) and a chained run restores it and sends ONLY the steering note (`steering.md`, worker-written, unlinked when absent) as the follow-up message - replaying the whole task would double the context the restored history already carries (`LLM_CACHE_KEY` is per-workspace, so the restored prefix hits the provider's prompt cache). The state belongs to ONE chain: `_prepare_runner_inputs` deletes it for any unchained run, because legacy single-checkout mode reuses `.openvisor/` across requests and request B must never resume request A's session; any load failure in the runner wipes the state and falls back to a cold session, so a corrupt resume can never kill a build (`_steering_note`, anchored on the pre-restamp `dev_run_started_at` captured at run start - never on "the agent's last message", which the run's own "Resuming…" narration would instantly mask - newest `STEERING_MAX_MESSAGES`/`STEERING_MAX_CHARS` kept; **§steering scope**: a SCOPED request run folds its OWN thread only - main belongs to the project (chat proposals, plan gates, talk about other work), and sweeping it is how two parallel pricing runs each shipped a LinkedIn footer when a main-chat ask was classified into its own request AND folded into both unrelated dispatches as "newer guidance"; the MVP/unscoped build keeps main, where main IS the build conversation - and both `_dev_thread` and the steering scope key on the BOUND run's request, never the `dev_request_id` mirror a parallel sibling can restamp mid-dispatch), so an "@agent do X" left on a parked run - or a whole conversation about the failure, in either thread, including notes left mid-run - actually reaches the next run. Before the PR opens (GitHub) or the MR merges (GitLab), the §14.5 boot gate test-boots the demo stack in a throwaway `verify-<id>` sandbox - a build whose app never answers HTTP is bounced back to the agent (`DEV_BOOT_FIX_ATTEMPTS`, default 1) instead of reaching the customer. The customer accepts the demo with **Approve delivery** (`approve-delivery` → finished). The sandboxed runner reaches the self-hosted GitLab via `GIT_EXTRA_HOST` (host:ip, Tailscale here); on K8s the nodes are not on the tailnet, so `.env.k8s` points the ip slot at the Tailscale-operator egress Service instead (`k8s/tailscale-egress.example.yaml` - setup, CGNAT-collision workaround and verification steps in its header) and the deployer resolves the name to an IP at Job dispatch (`hostAliases` accepts only IPs). WORKER-side git transports honor the same mapping through `_git_host_rewrite` (`git -c url.<mapped>.insteadOf=<original>` on the root-workspace refresh and the `_agent_branch_merged_ssh` merge probe, service name resolved at connect time) - the worker pod has no hostAliases, so without the rewrite a tailnet-only git host resolves publicly and its SSH port times out, which parked DELIVERED platform runs as failed at the post-merge refresh; `_refresh_root_workspace` also surfaces the failing git command's stderr into its error (a bare CalledProcessError hid the ssh timeout behind "exit status 128"). When a SANDBOX still finds no route to the remote it never builds blind (§sandbox git preflight): after a failed fetch the entrypoint probes `git ls-remote` (twice, 45 s each) and, for a run that must publish, exits **6** with `GIT_REMOTE_UNREACHABLE` - or `GIT_REMOTE_DENIED` when the host answers and refuses the key - before the agent session opens, so a severed path costs seconds and zero tokens instead of a whole build whose work could never be pushed. `_dispatch_runner` re-rolls only that unreachable verdict into a fresh sandbox (`_GIT_PREFLIGHT_ATTEMPTS`, 3 dispatches): the K8s deployer stamps every dev Job with a distinct `openvisor/dispatch` label so each attempt draws a NEW CNI security identity, because the fault is pinned to that identity - Cilium encodes it in the packet mark and the Tailscale egress proxy routes `fwmark 0x80000/0xff0000` out of its tailnet table, so one identity in 256 severs a pod from the git host for its whole life (`k8s/tailscale-egress.example.yaml` §5b). An exhausted budget parks with infrastructure copy (`_runner_exit_copy` reads the verdict first: the agent is blameless and nothing was billed), a refusal parks immediately with the deploy-key hint, and an empty/new repository - which answers ls-remote - still builds, as does a plan-only pass, which publishes nothing. Keep `OPENHANDS_ENABLED=0` for fast tests / deterministic demos (scaffold fallback - still pushes a real PR through the GitHub path via `SKIP_AGENT=1`). The SDK API is version-sensitive - re-verify `run_dev.py` when bumping `openhands-ai`. Dev-run token metering (§14.6): the runner dumps its accumulated LLM usage to `.openvisor/usage.json` (best-effort, written even on error/cap via try/finally, recreating `.openvisor/` if the agent deleted it - it is gitignored, so a `git clean -fdx` takes it out; `emit_event`/`live_events.py` self-heal the same way) and the worker bills it through `services/llm.record_usage` right after each dispatch (`_bill_dev_run`), updating `tokens_consumed`/`cost_credits`/org balance + a `consumption` transaction. A run killed by the deployer timeout writes no report - those tokens go unmetered, which is another reason the timeout + iteration caps matter; any agent run that leaves no report logs a warning and posts a "session not metered" feed event so a recurring metering hole gets noticed. Because `run_development` is synchronous and the task is not acks_late, a worker that dies mid-run (restart, OOM, node failure, redeploy) would otherwise leave the project stranded in-flight forever with the dev job orphaned; the `dev_run_reaper` Beat job (§14.x) closes that gap - it parks any run still in-flight past `DEV_RUN_TIMEOUT_MINUTES + DEV_RUN_REAP_GRACE_MINUTES` (default 10) as a normal failed+resumable run and best-effort meters any `usage.json` the runner had already written, so a killed run self-heals to a Resume-able state instead of hanging with unmetered spend.
