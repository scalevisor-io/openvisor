# Code map - Openvisor

The detailed tour of every subsystem, split out of [CLAUDE.md](../CLAUDE.md) so
that file stays a working brief rather than a reference manual. CLAUDE.md keeps
the rules, the workflow and a one-line index of these paths; this file is where
the detail lives.

`§N` references point at the platform's internal product spec, which is not
shipped in this repository - treat them as stable anchors, not links.

Same doc rule as everywhere else: a change that alters behavior described here

only - never narrates removed behavior.

## Subsystems, path by path

- `backend/app/services/statuses.py` + `lifecycle.py` - the §8 status machine. `can_transition()` is the single source of truth; `transition_async` (API) and `transition_sync` (Celery) apply side effects: `status_change` row, system chat message, WS event, notification emails. Admin can move anywhere; customer/agent can always push to `awaiting_admin`; the agent can never approve, price, or advance.
- `backend/app/services/project_actions.py` - the shared customer-action service layer (§hub pass-through P0): `evaluate`/`submit`/`require_review`/`request_help`/`retry_build`/`stop_build`/`approve_delivery`/`validate_request`+`cancel_request` (§requests: the human closes an AI-handled request by hand - validate = done with its awaiting_merge run closed and the mirror repointed, cancel = rejected with the run parked failed and the work unit ended sweep-style, pointers cleared, console settled idle; neither ever touches a live build; §12 one-click confirm: `start_request` on a still-`proposed` request posts the canned "Go ahead" reply + the agent's "On it" ack to main, and `cancel_request` on one posts "Not now" + the drop ack - the deterministic twins of the chat confirm verdict, freezing the proposal ack's ✓/✗ panel (shared-ui `ConfirmPrompt`, `Message.meta {kind:"confirm_request"}`) whichever surface acted)/`post_chat_message` (+ `valid_thread`) hold every action's guards + side effects keyed on `(db, project, actor)` - never on a session User - raising `ActionError(status, detail)`. §threads Request #0: `create_mvp_request` (called inside both project-create transactions for ai-kind) births the initial build as a `type='mvp'` Request (title "Initial build", thread seeded with the description) so `_dev_thread` narrates MVP runs into it (fallback main for pre-threads projects), `_bill_dev_run` attributes MVP usage to it, dispatch marks it `in_progress`, and a TERMINAL project transition closes it - owned by `services/lifecycle` (not `approve_delivery`) so every route agrees: `finished` → `done` (a delivery the customer accepted), `canceled` → `rejected` (nothing was delivered, and the request must not claim otherwise), already-closed rows untouched. Owning it in the one chokepoint is what stops an admin status change - or a project with no MVP phase, where `validate_request` refuses mvp rows and `approve_delivery` waits on a demo that never comes - leaving Request #0 stranded `in_progress` forever; it is server-side only (client schemas' type Literal), `start_request` 409s it, `handle_request` ignores it, and the plan-gate approval QuestionPrompt stays pinned to main (orchestrator decisions in main, narration in threads). The SPA routes in `api/projects.py`/`api/chat.py` are thin wrappers (role → actor, HTTP mapping, serialization), and the forthcoming hub pass-through routes will wrap the SAME functions, so the two surfaces can't drift. §request help: `request_help` is the FREE twin of `require_review` - same destination (`awaiting_admin`, so one consultant queue and the §8 admin email), no charge and no `credit_transaction` row, and offered only while `Project.dev_run_fault == "platform"` (`serializers.dev_help_capability`, the same verdict the button renders). The narrowness is the product decision: the platform pays for its own faults, the customer's own build failures keep Resume/Start fresh and the paid review. Each action commits (the service is the transaction boundary). Add new customer actions here first, then wrap.

- `backend/app/services/github.py` - GitHub provider (mirror of `gitlab.py`) for customer-owned repos: `is_github`/`parse_repo`, `ensure_base_branch` (seeds `main` on an empty repo so a PR has a base), `open_pr`/`find_open_pr`/`get_pr`, `check_repo_access` (auth check gating auto-merge). Deploy keys push the branch; PR creation needs `GITHUB_TOKEN` (deploy keys can't open PRs). Both providers also answer the §push preflight's two heals - `resolve_moved` / `customer_resolve_moved` (where a renamed or transferred repo went) and `ensure_deploy_key` / `customer_ensure_deploy_key` (make the project's key usable there with write access through the token - POST first, and only then repair: GitHub removes a read-only copy on THAT repo before re-adding, GitLab ENABLES the instance's existing key object (`platform_deploy_key_id` from the platform repo) and PUTs `can_push` - nothing ever detaches a key it cannot put back, because a detach followed by a duplicate-fingerprint refusal once left a production repo with no key) plus, on the platform's own forge, `customer_grant_member` / `platform_user` (GitLab authorises a deploy key's pushes as the account that INSTALLED it, so the platform account gets Developer access back on a project transferred out of the platform group). `gitlab.py` mirrors this for a CUSTOMER GitLab host (the `customer_*` fns + `is_gitlab`/`parse_repo_path`/`check_repo_access`, all taking base_url + a per-project `GITLAB_TOKEN`) separately from the platform-GitLab functions. An instance knows its OWN GitLab by two hostnames that need not match - `GITLAB_URL`'s (what `/api/v4` answers on) and the optional `GITLAB_SSH_HOST` (what git dials, e.g. `git.example.com:10022`) - and `is_platform_host` is the single place that decides whether a remote is ours (§ssh remotes). Multi-repo (§): every connected repo is a **working repository** - the runner shallow-clones each non-push repo read-only into `.openvisor/context/<name>` (worker writes `context_repos.txt`, task lists the paths) - and a project builds into its **push repo** - a connected repo (`ProjectRepo`, `provider`/`is_push_target`/`auto_merge`/`squash_on_merge`/`summarize_to_issue`) marked `is_push_target`, else the platform GitLab repo; the repos API (`api/projects.py`, `POST/PATCH/DELETE /projects/{id}/repos*` + `verify-auth`) enforces exactly-one push target and gates enabling `auto_merge` on a passing server-side auth check. - `runner/` - the OpenHands dev runner image (one sandboxed container per build). `run_dev.py` drives the OpenHands SDK v1 (`get_default_agent(llm)` + `Conversation(workspace="/workspace", max_iteration_per_run=LLM_MAX_ITERATIONS)` - the cap is a constructor arg and the SDK swallows unknown kwargs, so the driver verifies it landed and warns when an SDK bump silently drops it; the preset condenser is swapped by `_tuned_condenser` for a `RetryingCondenser` because condensation is the one chat-completions call in a build - agent steps ride the Responses API on gpt-5-family models - and litellm never retries 4xx, so a transient provider rejection there used to kill whole runs; the same swap widens the condenser's window to `DEV_CONDENSER_MAX_SIZE` (default 240; 0 keeps the preset's), because the preset default (measured: 80) leaves the agent a ~40-event working memory - a metered production run condensed 68 times in 60 minutes and read 44 distinct files 373 times for a single edit, re-reading its own task file 16 times - and every condensation also rewrites the prefix the run's prompt cache was built on: re-sending a cached prefix costs a tenth of re-deriving it and costs no agent step, so the window is WIDENED rather than removed, condensation staying the backstop against a context-window overflow); the driver also extends the preset's tool list with `grep`/`glob` and (§exploration budget) `task_tool_set`, the SDK's sub-agent delegation toolset the preset leaves off (`get_default_tools(enable_sub_agents=False)`) - without it every file a run ever opened stayed in the ONE main context and was re-uploaded on every later step, the dominant input-token line on a real build, whereas a sub-agent reads in its own context and returns a summary. **§delegated page reading**: that toolset delegates to a roster the SDK ships EMPTY (`get_factory_info()`: "No user-registered agents yet"), so enabling the tool alone gave the agent nothing to delegate to; `_register_web_researcher` fills it with one sub-agent, `web researcher` (the name the SDK ships a worked example under, so the example lands in the tool description for free), built by `agent_definition_to_factory` from an `AgentDefinition` carrying the run's `browser`/`websearch*` MCP servers and NO local tools - it reads public pages in its own context and returns the values with their URL, so a ~50 kB pricing-page snapshot never enters the main conversation, and with no file/terminal tool nothing it opened can reach a commit. Context7 and the consultant's MCP KBs stay with the main agent. Registration happens BEFORE the Conversation (the Task tool renders its roster into the tool description at creation time) and is best-effort, so on SDK drift the main agent simply keeps browsing itself; - `donsetch/` - the web-research sidecar image (§web research): the [DonSeTch](https://github.com/dondai44423/donsetch) engine plus `bridge.py`, which is the adapter between it and this platform. The engine speaks MCP on **stdio only**, but every MCP server injected into a run is addressed by URL, so the bridge serves `POST /{caps}/mcp` and proxies each request to a `donsetch mcp` subprocess over newline-delimited JSON-RPC. The capability set rides in the path (see the §Tools bullet above) and is enforced twice - `tools/list` hides what is off and `tools/call` refuses it - because a filtered list is a courtesy to the model, not a gate; a tool name absent from `TOOL_CAPS` stays hidden, so a future engine release that adds a fourth tool must be reviewed in before any run can call it. One engine process per MCP session, mirroring the browser sidecar's `--isolated` profile: a run's cookies, page memory and search handles are born on `initialize` and die with the session, so one project's browsing state never surfaces in another's build, and sessionless callers (the tool-poisoning vet, which fetches `tools/list` once before every build) get a short-lived process of their own rather than a run's. The engine refuses private and loopback targets itself (`guard.ssrf`), which is what keeps a `web_fetch` on the `internal` network from reaching postgres, redis or a cloud metadata endpoint. - `backend/app/services/stripe_svc.py` + `services/countries.py` - §18 billing details and invoicing. Every path that moves money issues an INVOICE, never a bare charge: a Stripe receipt carries no invoice number and no supplier registration number, so a business customer cannot file it. The invoice renders from the Stripe **customer**, so `ensure_customer` + `sync_customer` push the legal name, the billing address and the customer's tax number across BEFORE a session is created (this was collected and never sent until 2026-08-25, which is how a paying organization received a receipt addressed to nobody). Tax is **exclusive**: the customer pays the amount plus tax and the wallet is credited the amount, because taking it out of the credit would make every published rate wrong by the local percentage. An **incomplete** address is withheld whole rather than sent partial - a partial one resolves to the WRONG rate instead of to an error - and a subdivision goes only to countries that bill by one (`countries.needs_subdivision`; the EU bills nationally). `countries.tax_id_for` is the only thing that turns a typed tax number into a Stripe tax id, and it returns None rather than guessing: Stripe validates the format and that call sits in the middle of a payment. `billing_name`/`billing_tax_number` gate both on the account TYPE - a company name and VAT number survive a switch to individual so a round-trip loses nothing, and in the EU a stray customer VAT number would move a personal invoice to reverse charge and zero its tax. `tax_registrations()`/`warn_if_not_registered_for` exist because an account with no registration does NOT fail: it sells at zero tax and accrues a liability silently, so the noise has to be ours. The sidebar has two mutually exclusive forms and **820px is the single breakpoint that picks one**, declared twice on purpose: `DRAWER_QUERY`/`useNarrowLayout` in `lib/narrow.ts` (the project page's chat rail reads the same hook, so the drawer and the chat sheet can never disagree about what a phone is) and `@media (max-width: 820px)` in the stylesheet - change one and you change the other. Wide, it is a grid column that remembers a collapse into an icon rail (`app:sidebar` in localStorage), and the header's left slot carries the alpha chip. Narrow, the rail affordance is off (the remembered collapse must not reach the drawer), the same `<aside>` becomes an overlay drawer closed by a navigation, Escape, the backdrop or its own ×, and the header's left slot carries the drawer handle instead - a phone has no room for both. Closed, the drawer is off-canvas AND `visibility: hidden`, so its links leave the tab order rather than lurking off-screen. The project page's chat rail switches at the same width: a column beside the work wide - retracting to a TAB (its own surface, a hairline and a filled accent caret), because what is left after the panel goes has to still read as a control - a sheet floating OVER the page narrow (`.project-chat-rail` fixed at `z-index: 100`, above the drawer's 90 - the chat is the control surface and must stay reachable), collapsing to a thumb-reachable bubble that opens it. There it starts closed whatever `project:chat-rail` remembers - that preference is about a column - and closes again on a tap outside, on Escape, or as soon as it navigates.

- `services/project_defaults.py` + the `default_kb_ids`/`default_tools_off` fields on `GET`/`PUT /api/admin/settings` + the "What a new project starts with" card in `pages/admin/AdminSettings.tsx` - **§project defaults**: the knowledge bases and tools a NEW project is created with, chosen per `Project.kind` (`ai`, `auto_dev`, `direct_quote`, `chat`). The two gates default OPPOSITE ways, so the stored maps are not symmetric: `default_kb_ids` is a SELECTION (a KB reaches a project only if `kb_ids` names it) and `default_tools_off` is an EXCLUSION list (a tool reaches every project unless a `ProjectToolConfig` says otherwise) - which is why a tool row added to the instance later still reaches new projects, and why a default can never force-enable a globally disabled tool. The MODEL half of the card is the exception: `default_model_endpoints` ({kind: endpoint_id}) is stored here but resolved on every call by `model_config.project_endpoint`, never stamped - see that entry. `apply()` runs in BOTH wizard create paths (`api/projects.create_project` and the hub pass-through `api/hub.py`) right after the flush, stamping `kb_ids` and adding an `enabled=false` `ProjectToolConfig` row per excluded tool; ids whose row was deleted since are dropped there (a dangling `tool_id` would be a foreign-key error on the customer's create click) and the `PUT` validates every id against a live row (422, nothing persisted). The stamp happens ONCE: editing the defaults never reaches back into existing projects, whose per-project modals stay the truth. The `mcp` kind is absent on purpose - an MCP project snapshots the live retrieval sources instead (`mcp_projects.default_kb_ids`), because consulting them is the whole reason it exists. Motivating case: a `chat` project is the KB answering conversationally, and one born with no selection can only answer "I don't have anything on that in the knowledge base" until an admin visits its settings.

## Chat images (§chat images)

Images pasted, dropped or picked into a chat thread, sent to the model as OpenAI content parts.

- **§chat images → sandbox**: the screenshots also reach the dev agent. `workers/tasks.py::_stage_chat_images` (called per dispatch from `_prepare_runner_inputs`) stages the conversation's images under `.openvisor/images/` with a manifest (`images.json`), vision-gated at dispatch time (the model can change after upload); thread scope mirrors §steering scope (a scoped request stages its OWN thread, MVP/unscoped adds main) and a chained run stages only images its predecessor never saw. That scope is only correct because filing a request from main copies the ask DOWN into the request's thread, so `_seed_request_thread` copies the message's ChatImage rows with it - without that half, a screenshot sent where work is actually described (11 of the first 13 images this platform ever received) sits in a thread no build reads, and "fix what this screenshot shows" reaches the agent as prose. The rows are copied, not moved: a ChatImage belongs to one immutable message, and main must keep showing what the customer sent. The task gains a "Conversation screenshots" block (customer-supplied data, rule 11), and the runner (`run_dev.py::_with_images`) attaches the staged files as inline data-URI `ImageContent` parts on its first message - fresh runs on the task, resumed runs on the steering note - falling back to plain text on any SDK refusal so an image can never fail a build.

- **The capability question has no standard answer.** `/models` returns ids, never capabilities, so `ModelEndpoint.supports_images` is a stored TRI-STATE: `null` (nobody checked), `true`, `false`. The endpoint Test probe IS the discovery - it posts a 1x1 PNG as an `image_url` part and reads the answer; a 400 naming image/vision/content-type is a `false`, anything else (rate limit, outage) leaves the stored verdict alone so a blip can't record a false negative. `supports_images_source` is `probe` or `admin`, and an admin declaration outranks a probe and survives later tests. The instance-default model has no endpoint row, so it carries the same declaration as an `AppSetting` (`default_model_supports_images`).
- **One resolver, two twins.** `services/vision.py` answers `{enabled, reason, model}` over the SAME endpoint resolver the calls use (`model_config.project_endpoint`: saved endpoint → legacy inline → per-kind default → instance default), async for the API and sync for the workers, so the chat box and the worker can never disagree. `reason` is the tooltip on the disabled attach button and distinguishes "hasn't been checked" from "can't read images".
- **Storage and claiming.** `ChatImage` rows hold the bytes in-DB (like `ProjectFile`), immutable like the messages they belong to. Upload (`POST /projects/{id}/chat-images`) is gated on the verdict server-side and sniffs the MAGIC BYTES rather than trusting the client's content-type; the message then claims ids via `image_ids`, and `link_to_message` only claims rows that are unlinked, in this project, by the same author - so a message can never adopt someone else's image and an id can never move between messages. The claimed set is recorded on `Message.meta.images` so any reader renders them without a second query.
- **Sending them.** `tasks._message_content` inlines the bytes as data URIs in OpenAI content parts, but only when `vision` says the project's model supports images - a model downgraded after the fact degrades to plain text instead of erroring.

## The dev pipeline end to end (§14)

- OpenHands is real and fully automated (`OPENHANDS_ENABLED=1`): `run_development` checks out the project repo into the workspace, runs the headless SDK build (the runner image - `${COMPOSE_PROJECT_NAME:-openvisor}-runner` for `make dev` via the `build-runner` target; the registry-qualified `.../runner:<tag>` for `make prod`/K8s via `prod-build`, which the compose/chart deployer's `RUNNER_IMAGE` points at) with the §working-method plan gate ahead of it for fresh ai-kind MVP builds (PLAN-ONLY sandbox pass → `.openvisor/plan.md` → chat QuestionPrompt approval, deterministic approve/feedback branch in `classify_chat_message` before the LLM, `Project.dev_plan`/`dev_plan_status`, `DEV_PLAN_CONFIRM`/`DEV_PLAN_MAX_ITERATIONS`), and the runner pushes the run's branch - LLM-named BEFORE anything is committed (prompt #17 `branch_name.md` over the description/policy + scoped request + a targeted KB retrieval for stated naming conventions, honoring any customer branch convention like `f/#-`; sanitized by `naming.sanitize_branch`, persisted as `Project.dev_branch`, kept across resumes, cleared by `handle_request` per new request AND re-derived when the published branch was deleted on the push repo - a closed PR/MR whose branch is gone reads as rejected work, so `_reset_stale_branch` (best-effort, github + customer-gitlab) drops the stale name/PR pointer and the naming prompt re-runs against the current KB; fallback `agent/mvp`). Provider paths (chosen by `_dev_target`'s push repo, §multi-repo): (a) **customer GitHub/GitLab**: the runner pushes over the deploy key with a plain push, the worker opens a PR/MR (per-project `GITHUB_TOKEN`/`GITLAB_TOKEN`; empty repos are seeded with a base `main` first) whose description prefers the agent-authored management-level summary the run wrote to `.openvisor/pr.md` (prompt #5 v10 asks for it; worker-side `_agent_pr_body` redacts platform secrets, drops it wholesale on PEM material, reset per dispatch, template fallback - auto_dev copy never promises a demo redeploy), and with the push repo's `auto_merge` on it runs the §14.7 security-review→merge→fix loop (`_remote_auto_merge`, provider-agnostic via an `ops` adapter), else the customer merges and `dev_pr_sweep` deploys - watching the open change's head-commit CI meanwhile and auto-fixing a failed pipeline (§14.10 CI watch). (b) **other host**: plain branch push, the customer merges, `dev_pr_sweep` detects it over SSH. (c) **platform GitLab**: push options open the MR with NO title option (the entrypoint interpolates no dynamic text, and GitLab applies `merge_request.*` push options to the EXISTING MR on every later push - a fixed title used to retitle agent-authored MRs on each recovery dispatch) which the worker then personalizes - request/project title + the agent's `.openvisor/pr.md` summary via `_personalize_platform_mr` (`gitlab.update_mr`, best-effort, also on reaper recovery; NEVER a downgrade: `_is_generic_mr_title` keeps an agent-authored title, a dispatch that left no pr.md keeps the existing description, and `_strip_commit_trailers` drops Co-authored-by/Signed-off-by noise from pr.md and from whatever description is shown); when the agent committed AND pushed its branch ITSELF the entrypoint's push is an up-to-date no-op and no push option fires, so the worker opens the MR itself (`_open_platform_mr` fallback, personalized copy, loop + reaper recovery; the runner's wrapper commit is best-effort and the push happens regardless) - and auto-merges on green OCPA CI (`merge_when_pipeline_succeeds`, or direct-merge without `.gitlab-ci.yml`). A merge conflict / failed CI / timeout leaves the project in `awaiting_admin` or `awaiting_customer` - on the platform path a timed-out or MR-less run parks failed+resumable exactly like the customer path (never deploying unpublished workspace state or finalizing a request). **§14 no-target guard**: a project with NO repository at all - platform provisioning 400'd on the name and no repo is connected - used to fall past every `target is not None` gate (plan, model preflight, push) into the deterministic scaffold and DEPLOY it as the delivered MVP: a placeholder TODO app live in under a second, no LLM call, the customer's brief never read, and a demo email sent. `_run_development_impl` now resolves the target FIRST, retries the provisioning, and parks `awaiting_admin` + `dev_run_fault='platform'` with nothing built or billed. Every run is bounded by `DEV_RUN_TIMEOUT_MINUTES` (deployer kills an over-running container and reports a timeout - not exit 0) and the agent iteration cap - `DEV_MAX_ITERATIONS_DEFAULT` (instance default, legacy env name `DEV_MAX_ITERATIONS` still read) overridable per project by `Project.dev_max_iterations` (the admin card's Agent-iterations field, 1-500, null = default; resolved at dispatch) - the fail-safes against runaway token spend (keep the DEFAULT tight - raise per project, failure is slow and success is fast); **§investigation runs**: not every task is a diff - "check whether X still holds", "audit Y", "see if Z drifted and open a change if it did" are COMPLETE when nothing is wrong, and the pipeline used to record exactly that as a failed empty build. Prompt #17 step 9 asks the agent to write its findings to `.openvisor/report.md` and finish without committing; `_fail_no_changes` reads that artifact FIRST (`_agent_report`, same channel and the same PEM-drop/secret-redaction pass as `pr.md`) and routes to `_finish_investigation` - the report is posted into the request thread as the answer, the request closes `done` (no PR to wait on: the report IS the delivery) and the run is saved `done`. Guarded to SCOPED requests: an mvp build, or a run with no bound request, still fails on an empty result however eloquently it explains itself, and a run that wrote no report keeps the old failed+resumable park. Letting the AGENT declare the outcome is what keeps the two apart - intent is never guessed up front - and prompt #17 step 10 makes the declaration STRUCTURED (§run outcome): every session ends by writing `.openvisor/outcome.json` `{outcome: changed|no_change_needed|blocked, summary}`, and `_fail_no_changes` cross-checks it against the evidence. `no_change_needed` (or a bare report.md, the v13 back-compat) closes the investigation; `changed` with no publishable diff fails with the DISCREPANCY named ("reported a change but nothing was committed" - the prod run that declared a deliberately-untracked runbook delivered); `blocked` fails with the agent's own blocker as run_error. Missing/malformed declarations degrade to the artifact-only behavior, so a non-compliant agent changes nothing. **§findings ledger**: both write-ups are assembled from `.openvisor/findings.md`, which step 7 asks the agent to append to WHEN it makes an observation rather than to reconstruct at the end - a prod price-drift run found a live billing exposure inside a line of reasoning it then abandoned and, twenty steps later, reported that no such exposure existed; every line of the ledger must reach the write-up or be dismissed there, and `_prepare_runner_inputs` wipes it per dispatch like `report.md`/`outcome.json` so a run can never report an observation it did not make. Its companion in rule 6 covers the figures themselves: never a price/version/limit from memory, always a source opened in THIS session and named where the figure is reported - the same run confirmed a provider's list price by solving backwards from our own published price until the implied rate matched, which checks our data against itself. Otherwise a failed/timed-out run parks the project in `awaiting_customer` with the log kept, and the customer's **Resume development** button (`retry-build`) re-runs it; its sibling **Start fresh** (`retry-build {fresh:true}`, §run chains) DISCARDS the chain instead - every failed run of the request is superseded, the new run is unchained with its own isolated dir in every mode (at limit 1 chaining would reuse the canonical checkout with the discarded work still in it) and naming reserves the request's PRIOR branch names so the fresh branch gets a suffix - because the entrypoint continues `origin/<branch>` and even local unpushed commits, a same-name "fresh" run would silently resurrect the abandoned work. `_save_run`'s shadow-ledger branch backfill applies to CHAINED rows only - stamping the stale scalar onto an unchained row made naming early-return, which is exactly how prod's first Start fresh re-landed on the abandoned branch. The publish gate counts a COMMITTED non-plumbing .gitignore change as a real deliverable (`BRANCH_GITIGNORE_REAL`): excluding .gitignore wholesale from the branch diff told a customer "nothing was committed" over a commit sitting right on the branch, while the pure `+.openvisor/` plumbing line still blocks - folding every customer/consultant message posted in the main thread AND the run's own narration thread (`_dev_thread`) since the previous dispatch into the task as a bounded, author-labeled **steering transcript**, and (§conversation resume) the resumed run REHYDRATES the previous agent session itself: the runner persists the SDK conversation under the workspace's `.openvisor/conversation/` (stable id in `conversation_id`, `delete_on_close=False` - verified against the pinned openhands-ai) and a chained run restores it and sends ONLY the steering note (`steering.md`, worker-written, unlinked when absent) as the follow-up message - replaying the whole task would double the context the restored history already carries (`LLM_CACHE_KEY` is per-workspace, so the restored prefix hits the provider's prompt cache). The state belongs to ONE chain: `_prepare_runner_inputs` deletes it for any unchained run, because legacy single-checkout mode reuses `.openvisor/` across requests and request B must never resume request A's session - EXCEPT a fix dispatch (boot/CI/security), which is the SAME `DevRun` row taking another pass rather than a new chain, so it keeps the session and its fix text rides `steering.md` as well as the task (the resumed branch sends steering.md INSTEAD of replaying task.md, so a fix written only into the task would never reach a rehydrated agent); wiping there made every retry re-explore the repository from cold before it could act on a one-line failure, while Start fresh - deliberately unchained - keeps its wipe. Any load failure in the runner wipes the state and falls back to a cold session, so a corrupt resume can never kill a build (`_steering_note`, anchored on the pre-restamp `dev_run_started_at` captured at run start - never on "the agent's last message", which the run's own "Resuming…" narration would instantly mask - newest `STEERING_MAX_MESSAGES`/`STEERING_MAX_CHARS` kept; **§steering scope**: a SCOPED request run folds its OWN thread only - main belongs to the project (chat proposals, plan gates, talk about other work), and sweeping it is how two parallel pricing runs each shipped a LinkedIn footer when a main-chat ask was classified into its own request AND folded into both unrelated dispatches as "newer guidance"; the MVP/unscoped build keeps main, where main IS the build conversation - and the whole run pipeline keys the request it builds on the BOUND run's request through `dev_concurrency.run_request` (task text, branch naming, PR recording, billing, work summary, investigation close-out, security-review/acceptance metering, `_dev_thread` and the steering scope alike; None = an MVP/unscoped build), never the `Project.dev_request_id` mirror, which follows the newest STARTED run (restamped by `run_development` at run start) and is cleared by whoever finishes first - reading it mid-run is how a Start fresh on one request was handed its parallel sibling's task and shipped the sibling's change under its own row, after which the sibling's own resume found the mirror cleared and built the MVP), so an "@agent do X" left on a parked run - or a whole conversation about the failure, in either thread, including notes left mid-run - actually reaches the next run. Before the PR opens (GitHub) or the MR merges (GitLab), the §14.5 boot gate test-boots the demo stack in a throwaway `verify-<id>` sandbox - a build whose app never answers HTTP is bounced back to the agent (`DEV_BOOT_FIX_ATTEMPTS`, default 1) instead of reaching the customer. The customer accepts the demo with **Approve delivery** (`approve-delivery` → finished). The sandboxed runner reaches the self-hosted GitLab via `GIT_EXTRA_HOST` (host:ip, Tailscale here); on K8s the nodes are not on the tailnet, so `.env.k8s` points the ip slot at the Tailscale-operator egress Service instead (`k8s/tailscale-egress.example.yaml` - setup, CGNAT-collision workaround and verification steps in its header) and the deployer resolves the name to an IP at Job dispatch (`hostAliases` accepts only IPs). PLATFORM-side git transports honor the same mapping through `repos.git_host_rewrite` (§ssh remotes: one resolver for the worker AND the API, both remote spellings; `git -c url.<mapped>.insteadOf=<original>` on the root-workspace refresh and the `_agent_branch_merged_ssh` merge probe, service name resolved at connect time) - the worker pod has no hostAliases, so without the rewrite a tailnet-only git host resolves publicly and its SSH port times out, which parked DELIVERED platform runs as failed at the post-merge refresh; `_refresh_root_workspace` also surfaces the failing git command's stderr into its error (a bare CalledProcessError hid the ssh timeout behind "exit status 128"). The same rewrite runs behind the repo card's **Verify SSH** and the default-branch probe (`repos.check_ssh` / `detect_default_branch`) and behind git KB fetches, which otherwise report an unreachable host for a correctly installed deploy key; both also canonicalise the remote first (`repos.normalize_ssh_uri`), because git's scp-like syntax has NO port field - a connected `git@host:10022/grp/repo.git` parses `10022` as the first path segment and dials port 22, so it is rewritten to `ssh://git@host:10022/grp/repo.git` on write (repo connect) and on read (`_repo_target`, healing rows stored before this), and their verdict quotes ssh's own first stderr line rather than git's closing access-rights advice. When a SANDBOX still finds no route to the remote it never builds blind (§sandbox git preflight): after a failed fetch the entrypoint probes `git ls-remote` (twice, 45 s each) and, for a run that must publish, exits **6** with `GIT_REMOTE_UNREACHABLE` - or `GIT_REMOTE_DENIED` when the host answers and refuses the key - before the agent session opens, so a severed path costs seconds and zero tokens instead of a whole build whose work could never be pushed. `_dispatch_runner` re-rolls only that unreachable verdict into a fresh sandbox (`_GIT_PREFLIGHT_ATTEMPTS`, 3 dispatches): the K8s deployer stamps every dev Job with a distinct `openvisor/dispatch` label so each attempt draws a NEW CNI security identity, because the fault is pinned to that identity - Cilium encodes it in the packet mark and the Tailscale egress proxy routes `fwmark 0x80000/0xff0000` out of its tailnet table, so one identity in 256 severs a pod from the git host for its whole life (`k8s/tailscale-egress.example.yaml` §5b). An exhausted budget parks with infrastructure copy (`_runner_exit_copy` reads the verdict first: the agent is blameless and nothing was billed), a refusal parks immediately with the deploy-key hint, and an empty/new repository - which answers ls-remote - still builds, as does a plan-only pass, which publishes nothing. Reachability is not write access, and reading is all a deploy key installed read-only, a key whose installer lost their push rights, or a repository that MOVED still does - all three fetch fine and refuse the final push after the whole build (prod 2026-08-26: 3.2M tokens into a two-line fix on a project transferred out of the platform's group, whose old path 301'd/405'd every API call and whose key, installed by the platform account, no longer pushed - GitLab authorises a deploy key's pushes as the account that installed it). So the WORKER proves the push before any sandbox exists (§push preflight, `_push_preflight` in `_run_development_customer`): `repos.check_push` pushes an empty commit to the hidden ref `refs/openvisor/preflight/<run>` - no branch, no CI, nothing in any UI - and deletes it, so the remote's own pre-receive checks judge exactly what the branch push will hear; `denied` (the remote's own words, `_push_cause`) first tries the self-heal - `_heal_deploy_key` makes the project's key usable there through the repo's `GITHUB_TOKEN`/`GITLAB_TOKEN` (`github.ensure_deploy_key` / `gitlab.customer_ensure_deploy_key`: attached with write access, never detached; on the platform's own GitLab also `customer_grant_member` for the platform account, the key's installer, whose membership a transfer out of the platform group strips) and re-probes - and only an unhealed refusal parks, before dispatch, with `_push_failure_hint`'s diagnosis (read-only key, lost installer, key unknown to the repo, wrong GitHub repo, protected branch), the heal's own failure reason when one was attempted, and nothing billed; `unreachable` from the worker is not a verdict on the key (the sandbox's route is the authority) and the build proceeds. Before that, `_heal_moved_repo` asks the forge where a renamed/transferred repository went (`gitlab.customer_resolve_moved` / `github.resolve_moved`: one GET, one followed redirect) and rewrites the connected row's path in place (`repos.replace_repo_path` keeps the scheme, user, host and port; §repo binding stays on the same row), telling the thread; the §auto_dev sweep follows the same move through `_poll_issues` instead of logging one 301 per minute, and any other polling refusal becomes the watch card's WHY. The repo card's Check SSH runs the write probe for the push target (`check_ssh(write=True)`), so the answer a customer reads there is the answer the build will get. Keep `OPENHANDS_ENABLED=0` for fast tests / deterministic demos (scaffold fallback - still pushes a real PR through the GitHub path via `SKIP_AGENT=1`). The SDK API is version-sensitive - re-verify `run_dev.py` when bumping `openhands-ai`. Model-endpoint OUTAGES are the other pre-dispatch verdict: `_model_preflight` treats a 5xx from `/models` as a suspicion the 1-token completion settles (re-asked once after `_OUTAGE_RECHECK_S`), and two 5xx park the run as an outage (`_MODEL_OUTAGE` copy: nothing to reconfigure, Resume later, nothing billed); inside a run, `run_dev.py` widens the SDK's `LLM_RETRY_EXCEPTIONS` with litellm's `BadGatewayError`/`APIError` so a 502 or a 52x from the CDN in front of the model gets the same bounded backoff as a 503 instead of ending the build. Dev-run token metering (§14.6): the runner dumps its accumulated LLM usage to `.openvisor/usage.json` (best-effort, written even on error/cap via try/finally, recreating `.openvisor/` if the agent deleted it - it is gitignored, so a `git clean -fdx` takes it out; `emit_event`/`live_events.py` self-heal the same way) and the worker bills it through `services/llm.record_usage` right after each dispatch (`_bill_dev_run`), updating `tokens_consumed`/`cost_credits`/org balance + a `consumption` transaction. A run killed by the deployer timeout writes no report - those tokens go unmetered, which is another reason the timeout + iteration caps matter; any agent run that leaves no report logs a warning and posts a "session not metered" feed event so a recurring metering hole gets noticed. Because `run_development` is synchronous and the task is not acks_late, a worker that dies mid-run (restart, OOM, node failure, redeploy) would otherwise leave the project stranded in-flight forever with the dev job orphaned; the `dev_run_reaper` Beat job (§14.x) closes that gap - it parks any run still in-flight past `DEV_RUN_TIMEOUT_MINUTES + DEV_RUN_REAP_GRACE_MINUTES` (default 10) as a normal failed+resumable run and best-effort meters any `usage.json` the runner had already written, so a killed run self-heals to a Resume-able state instead of hanging with unmetered spend.

- **§dev harness** - which agent driver a build runs on. The catalog is a code constant (`services/dev_harness.py`), not admin data, because a harness only exists if the runner image ships its driver script; the admin surface is three `AppSetting` keys - an enable flag (off by default), the allowed set, and the instance default - plus `Project.dev_harness` as the per-project pin (null = inherit). `resolve()` is the sole resolver and is fail-closed in the direction that matters: with selection disabled a stored pin is IGNORED, not merely hidden in the UI, so switching the feature off really does move every project back onto the default driver; a pin whose id was withdrawn or dropped by a release degrades to the default rather than failing the build, the way a deleted `ModelEndpoint` degrades to the global model, and so does a pin the project's MODEL cannot run (`model_hints` on the catalog entry, `model_supported()`): the `claude` CLI checks the model name against its own list before it ever reaches the gateway, so a project pinned to `claude_sdk` while its endpoint served `qwen3.6-35b-a3b` spun a sandbox up, cloned the repo and died on the first model call - production, 2026-08-30. The dispatcher passes the model to `resolve()`, builds on a harness that can run it, and says so in the build console; `_stamp_harness_version` passes it too, so the fingerprint records the harness that actually executed rather than the one pinned. The admin PATCH refuses an incompatible pin outright, because a stored pin that always degrades is a preference that silently does nothing. The resolved id rides `DevRunIn.harness` to the deployer, reaches the sandbox as `DEV_HARNESS`, and `runner/entrypoint.sh` maps it to a driver script - an id the image ships no driver for falls back to the OpenHands driver, so a newer platform dispatching to an older runner still builds. Everything around that one line (checkout, deploy key, secret export, leak scan, publish, exit codes) is the entrypoint's, not the driver's, which is what makes a second harness a driver rather than a fork of the pipeline. The harness is NOT hashed into the run fingerprint by id: it rides two fields `agent_eval/harness_version.py` folds in, and every registered harness MUST carry a distinct value of each. `tool_preset_id` says which tools the agent gets; `driver_revision` says which implementation hands them over, including the pinned agent-SDK version. The second field exists because a driver change can move cost by multiples while touching no tool, prompt or cap - enabling Anthropic prompt caching cut a build's input bill ~4x and produced a byte-identical fingerprint, so the cheap runs and the expensive ones aggregated as one harness. Bump `driver_revision` for ANY change to a driver script or its pinned dependency; adding the field moved every fingerprint once (schema 2), which is correct - runs before it were made by a harness whose driver build was not part of its identity. A second driver has to reproduce the whole `.openvisor/` contract the worker reads back - `usage.json` (or the run bills nothing), `error.json`, `exit_reason.json`, `plan.md` under PLAN_ONLY, `conversation_id`/`conversation/` for resume chains, the `live_events.py` feed, and the exit codes - and its model needs an `api_model` row in the price table before it is enabled, because `pricing.py` raises rather than billing 0. Two drivers ship today: `openhands` (`run_dev.py`) and `claude_sdk` (`run_claude.py`, the Claude Code agent loop as a library - Anthropic models only, since it speaks the Messages API rather than the OpenAI-compatible endpoint the other harness uses). The Claude driver's own traps, all found by running it: `bypassPermissions` maps to the CLI's `--dangerously-skip-permissions`, which REFUSES to run as root and the runner is root, so permissions are granted through the programmatic `can_use_tool` callback instead; the platform's `LLM_BASE_URL` ends in `/v1` while the Anthropic client appends its own version segment, so `_apply_base_url` trims it and skips the canonical host entirely; the SDK raises `ProcessError` carrying only "Check stderr output for details", so the driver captures the CLI's stderr itself and folds the tail into `error.json`; the feed KINDS are a contract (`shared-ui/BuildFeed` renders `title` and picks its icon off `kind`), so a driver emitting its own vocabulary renders as blank rows under a fallback icon - `_tool_event` maps the CLI's tools onto the same kinds `live_events._summarize_action` produces, and keeps model-composed arguments (a search query, an MCP tool's args) out of titles the way the leak-scan threat model requires; `ResultMessage` carries the session total and arrives only at the END, so usage is accumulated per assistant turn (`_absorb_turn`) or a stopped or wall-clock-killed run reports zeros and bills NOTHING, and the live console sits at ~0 credits for the whole build; and the CLI's default system prompt is written for an INTERACTIVE session, so the driver prepends `_HEADLESS_NOTE` (nothing will wake this agent - it must poll its own background work) and disallows the tools that promise a wake-up or fan out to a swarm (`ScheduleWakeup`, the Cron trio, `PushNotification`, `SendMessage`, `ListAgents`, `DesignSync`, `Workflow`) - without the note the agent backgrounded a build, said it would wait to be notified, and ended the session on unverified work. `max_budget_usd` gives it a hard per-run provider-side spend ceiling alongside the iteration cap and the deployer's wall clock - `DEV_RUN_MAX_USD`, set from `dev_run_max_usd` (0 = unset) and carried by both deployer paths; it is the only one of the three caps denominated in money, which is what the other two cannot bound when the model is expensive. And the staged `.openvisor/mcp.json` is written in the OpenHands spelling (`{"url": ...}`, no transport field), while the CLI's config is a DISCRIMINATED union - an untyped entry with a url reads as a stdio server with no command and is SKIPPED, so `_transport()` stamps `type` on every server before the session opens and `_report_session()` logs what the session actually got; without both, a build whose every tool was dropped is indistinguishable from one that had them. Measuring two harnesses against each other is `ci/bench/drive.py` + `agent_eval compare` (see `ci/bench/README.md`); `run_claude.py` also records the provider's own `total_cost_usd` as `provider_cost_usd`, which is what proved the cache-WRITE under-bill: writes now have their own rates (§18) and this harness turns out to write on the ONE-hour TTL, so a single 1.25x column would not have fixed it.
