# Openvisor - API contract (v1)

Base: same origin as the SPA (`app.openvisor.local` locally, `app.openvisor.example.com` in prod).
All routes below are prefixed with `/api`. WebSocket lives at `/ws/...`.
JSON everywhere. Auth = HTTP-only session cookie `session`. CSRF: fetch a token from
`GET /api/auth/csrf` → `{"csrf_token": "..."}` and send it back on every mutating request
(POST/PUT/PATCH/DELETE) in header `X-CSRF-Token`.

Errors: `{"detail": "human readable message"}` with 4xx/5xx status.
Datetimes are ISO-8601 UTC strings. Money/credits are numbers (float, 1 credit = 1 EUR).

## Auth

- `GET /auth/altcha` → Altcha challenge JSON `{algorithm, challenge, salt, signature, maxnumber}`
  (feed to the `altcha` widget, or POST solution manually).
- `POST /auth/signup` `{email, password, account_type: "individual"|"organization", company_name?, full_name?, altcha: "<base64 payload from widget>", accept_terms: true}`
  → 201 `{ok: true}` (sends verification email). Password min 10 chars. `accept_terms` must be `true` (ToS + privacy policy consent, stamped on the user as `tos_accepted_at`); otherwise 400. An `organization` signup requires `company_name` and `full_name` (the contact person); otherwise 400. VAT and the billing address are not asked at signup - they live on the account page (`PATCH /account`). The new account starts with `signup_credits` welcome credits (default 5) as a ledger entry of kind `signup`.
- `POST /auth/verify-email` `{token}` → `{ok: true}`
- `POST /auth/resend-verification` `{email}` → always `{ok: true}`
- `POST /auth/login` `{email, password}` → `{user: User}` + sets session cookie. 401 on bad creds; 403 with an explicit detail message when the account is blocked (§user blocking - checked after the credential check, so a wrong-password probe learns nothing). A blocked user's EXISTING sessions 401 (`"Account blocked"`) on their next request and their API tokens stop authenticating (403 `"Account blocked"`; the MCP server treats their tokens as unauthenticated).
- `POST /auth/logout` → `{ok: true}`
- `POST /auth/forgot-password` `{email}` → always `{ok: true}`
- `POST /auth/reset-password` `{token, password}` → `{ok: true}`
- `GET /auth/me` → `{user: User, org: Org}` or 401.

`User = {id, email, full_name (string|null), role: "customer"|"admin", email_verified: bool, created_at}`
`Org = {id, name, type, company_name, vat_id, address_line1, address_line2, postal_code, city, country (all string|null), credit_balance: number}`

## Account

- `PATCH /account` `{account_type: "individual"|"organization", full_name, company_name?, vat_id?, address_line1?, address_line2?, postal_code?, city?, country?}` → `{user: User, org: Org}`. Edits the signed-in user's account. `full_name` is always required. When `account_type` is `organization`, `company_name`, `address_line1`, `postal_code`, `city` and `country` are required too (400 listing what's missing); `vat_id` and `address_line2` stay optional. Switching back to `individual` keeps the stored company fields (nothing is wiped). `org.name` follows the type: the company name for organizations, the person's full name for individuals.

## Meta

- `GET /meta/specialities` → the enabled entries of specialities.json (full objects).
- `GET /meta/questions` → initial-user-questions.json content.
- `GET /settings` → `{brand_name, brand_slug, brand_color_primary, brand_color_secondary, consultant_name, consultant_first_name, credit_currency, specialities: [{id, label, description, short_label, icon, deliverable_type, knowledge_tags, capabilities, complexity_baseline}], intake: {ai_enabled, direct_quote_enabled, auto_dev_enabled, chat_enabled}}` - public white-label identity + enabled activity catalog; the SPA fetches it at boot (before auth) and applies the colors as CSS variables. `base_fee_credits` is the track's INSTANCE-EFFECTIVE engagement fee (an admin override from `PUT /admin/settings` wins over the specialities.json default). The speciality fields beyond `id`/`label`/`description` feed hub-side matching and engagement decomposition (§hub capability discovery); hub readers treat them as optional (fail-soft) because older spokes publish only the base trio. Defaults are the Openvisor identity; a spoke rebrands via the `BRAND_*`/`CONSULTANT_NAME` env vars. `intake` mirrors the admin deposit-pause flags for catalogs/hubs (§hub capability discovery) - advisory only, creation re-checks server-side; a reader missing the key (stale cache, older spoke) must treat availability as unknown and fail closed for routing. `chat_enabled` is OPT-IN (false until the admin unpauses chat deposits): chat exposes the knowledge base conversationally, so each spoke owner decides.
- `GET /meta/legal` → `{legal_name, legal_address}` - §legal identity: the operating company the admin set on the Settings page, both `""` when never set (a reader keeps its own built-in value). Public, unauthenticated, and the ONE route answering `Access-Control-Allow-Origin: *`: the landing is a static build served from another host, so its Privacy policy and Terms of service read this in the browser (payload is the same public identity those pages print, and a wildcard origin forbids cookies, so no credentialed data is reachable). Cached `public, max-age=60`, so an edit reaches the legal pages within the minute.
- `GET /meta/config` → `{deploy_env, deploy_domain, landing_base_url, credit_currency, alpha: true, gitlab_url, review_request_credits, chat_upfront_credits, pause_ai_deposits, pause_direct_deposits, pause_auto_dev_deposits, pause_chat_deposits}` - the `pause_*` flags are the admin-set deposit switches; the SPA grays out the matching option in the new-project wizard. `gitlab_url` is shown as the repo-path prefix in the admin program form (§28).

## MCP delegation (§MCP delegate) - token-authed, no session/CSRF

The MCP sidecar proxies these; they take a **project-scoped** `ov_` token (403 for a plain user or hub token).

- `POST /mcp/delegate` `{spec, type: "feature"|"edit"|"bug"}` → 201 `{request_id, title, type, status, created_at, pull_requests, tokens_consumed, credits, url, build_state}` - files the spec as a Request on the token's project and starts it, wrapping the SAME `services/project_actions.create_request`/`start_request` the SPA and hub use, so the §12/§14 guards can't drift. Returns immediately: the build takes minutes. 409 without a repository to publish into, 402 on an empty wallet, 429 past `MCP_DELEGATE_DAILY_MAX` AI requests/day on that project.
- `POST /mcp/consult` `{question}` → 202 `{job_id, state: "queued", note}` (§MCP consult, mode 1b) - answers a question about the project's OWN codebase by running the dev harness **read-only**: it reuses the §working-method plan pass (`plan_only`), so the runner clones the repositories, explores and publishes nothing - no edits, no commit, no push, bounded by the plan-pass iteration cap - and the answer is read back out of `.openvisor/plan.md`. Priced like a build, so `search_knowledge` remains the cheap path for anything the knowledge base can answer. 402 on an empty wallet.
- `GET /mcp/consult/{job_id}` → `{job_id, state: "queued"|"running"|"done"|"failed", answer?, error?}`. The **question is never persisted** (it rides to the worker and into the sandbox task) and the answer lives in redis under a 1 h TTL - nothing about a consult reaches the database. Answers pass the same defensive pass as the build feed: platform secrets redacted, verbatim knowledge-base spans withheld. Refused rather than queued when no run slot is free.
- `GET /mcp/delegations?limit=` → `{delegations: [...]}` (newest first, `mvp` excluded).
- `GET /mcp/delegations/{request_id}` → the same shape; 404 for a request belonging to another project.

The delegation **spec is stored** - it is the work order the build runs from and what the PR cites - unlike a consult question, which is never persisted. Neither endpoint returns the request's thread.

## Chat images (§chat images)

- `POST /projects/{id}/chat-images` (multipart `files`) → 201 `[{id, filename, content_type, size_bytes}]`. **409** when the project's model isn't known to read images (the gate is server-side; the disabled UI button is a courtesy), 413 over 5 MB, 415 when the MAGIC BYTES aren't PNG/JPEG/WebP/GIF - the client's content-type header is not trusted. Max 4 per message.
- `GET /projects/{id}/chat-images/{image_id}` → the bytes, `Cache-Control: private`. Access rides on the project dependency, so a read-only share sees the thread's images and nobody else does.
- `POST /projects/{id}/messages` accepts `image_ids: [...]` - ids uploaded above and not yet claimed. Unknown, already-claimed or another author's ids are ignored (messages are immutable, so an image can never move between them). The claimed set comes back on `Message.meta.images`.

## Model image support (§chat images)

There is **no capability discovery** in the OpenAI-compatible contract - `/models` returns ids, never capabilities - so whether a model reads images has to be stored, and it is stored per saved endpoint:

- `POST /admin/model-endpoints/{id}/test` gains `vision: {supported: true|false|null, detail, source}` alongside `chat_completions`/`responses`/`effort`. The probe sends a 1x1 PNG as an `image_url` content part: accepted → `true`, a 400 naming image/vision/content-type → `false`, anything else (rate limit, outage) → `null` and the **stored verdict is left alone**, so a provider blip can never record a false negative. A verdict an admin declared is never overwritten by a probe.
- `POST`/`PATCH /admin/model-endpoints` accept `supports_images: true` - the admin declaring a model multimodal when the probe can't confirm it. Stored with `supports_images_source: "admin"`, which outranks `"probe"`.
- `GET /admin/settings` / `PUT /admin/settings` carry `default_model_supports_images` (+ read-only `default_model`): the instance-default model has no endpoint row to hold a verdict, so the admin declares it there.
- `Project.image_support` = `{enabled, reason, model}` on the project payload. `enabled` is true only when something positively said yes; `reason` is the tooltip for the disabled attach button, and distinguishes "hasn't been checked yet" from "this model can't read images" - one of those is fixable by pressing Test.

## Usage (§usage graph)

- `GET /projects/{id}/usage?days=30` (1-365) → `{days, series: [{day, tokens, credits, mcp_tokens, requests_done, requests_canceled}], totals: {tokens, credits, mcp_tokens, lifetime_tokens, lifetime_credits, requests_done, requests_canceled, lifetime_requests_done, lifetime_requests_canceled}}` - daily consumption for the project's Usage tab. Built from `credit_transaction` (the only per-event token record: `tokens` is stamped by every metering path; project counters are running totals with no history), restricted to spend kinds (`consumption`, `mcp_query`, `program_run`) so a top-up never appears as usage. The series is DENSE - one bucket per UTC day including zeros - because a sparse series draws a chart that lies about the quiet days. `credits` are positive magnitudes (ledger amounts are negative debits). `requests_done`/`requests_canceled` count the requests FILED that day (bucketed on `Request.created_at`, its only timestamp) that closed `done` / `rejected` ("canceled" is the customer-facing name - cancel_request closes with `rejected`); the lifetime twins count across all time.

## MCP project tokens (§MCP project tokens)

- `GET /projects/{id}/mcp-tokens` → `{tokens: [{id, name, created_at, last_used_at}], usage: {queries_total, credits_total, queries_30d, credits_30d}}` - the project's MCP tokens and its query counters (the MCP tab). Counters only: **what was asked is never stored**, so there is nothing to return.
- `POST /projects/{id}/mcp-tokens` `{name}` → 201 `{id, name, created_at, last_used_at, token}` - mints a `project`-scoped `ov_` token. `token` is the plaintext and is returned ONCE (only its sha256 is stored). 409 past 10 tokens per project.
- `DELETE /projects/{id}/mcp-tokens/{token_id}` → `{ok}` - revoke. 404 for a token id belonging to another project or of another scope.

- `GET /mcp/tokens` → `[{id, name, created_at, last_used_at, project_id, project_name, project_kind}]` - every `project`-scoped token in the caller's org, with the project it is bound to; what the MCP tab of `/settings/tokens` groups by. Secrets never appear here.
- `POST /projects/mcp` `{title (1-255), description?: ≤4000, token_name?}` → 201 `{project, token, token_name, mcp_url}` - the one-click flow: creates an `mcp`-kind project AND mints its first token in one call, so the customer leaves with a working `claude mcp add` line. `token` is the plaintext, returned ONCE. 409 past 100 MCP projects per org.
- `POST /mcp/projects` `{title (1-255), description?: ≤4000}` → 201 `{project_id, name, status, next_step}` - the MCP `create_project` tool's backend. Bearer-token auth, no session/CSRF. ACCOUNT-WIDE tokens only: a project-scoped token is bound to one project and gets `403`. Returns NO token on purpose - an agent that could mint its own long-lived credential would write it into a transcript - so `next_step` points the customer at the project page to mint one. Rate-limited 10/60s per org.

A project token authenticates to the same MCP endpoint as an account-wide token, but the sidecar shows it only its own project's tools (no `project_id` argument exists on them). Knowledge answering is **exclusively** its job: `POST /knowledge/answer` needs the project to choose the model, narrow the knowledge bases and carry the cost, so an account-wide token is refused there.

## Projects (auth required; email_verified required to create)

- `GET /projects` → `[ProjectSummary]` (own org + projects shared with the caller (§sharing); admin sees all with `?all=1`).
- `GET /projects/search?q=&all=` → `{results: [ProjectSummary], ai: bool, reason: ("disabled"|"rate_limited"|"unavailable"|null)}` (§project search) - the dashboard search box, same scope as `GET /projects`. `results` is ranked most-relevant-first: a deterministic pass over the card text (name, speciality, kind, status, demo state) and the description, then - within the per-org cap - an **unbilled** LLM rerank (prompt #13) so intent-level queries work ("the game whose build failed"). `ai` says which ranking came back and `reason` why not, and the model can only reorder/filter what it was given: invented ids are dropped, and an empty model answer is ignored when the text pass did match. An empty `q` is the plain list. Never billed; `PROJECT_SEARCH_RATE_PER_10MIN` (default 40, per org) bounds the rerank and `PROJECT_SEARCH_AI_ENABLED=0` disables it - past either, the box keeps serving text matches. Must stay routed before `/projects/{id}`.
- `POST /projects` `{kind: "ai"|"direct_quote"|"auto_dev"|"chat", speciality?, description (1-40000 chars), from_scratch: bool, sovereign: bool, sovereign_comment?, repos?: [{ssh_uri}], issue_watch?: {labels[], assignees[], authors[]}}`
  → `Project` (status `draft`). `kind` defaults to `ai`. There is no `name` input: the title is generated server-side from the description (deterministic bootstrap at creation, refined by the LLM title prompt during evaluation unless the customer has renamed the project). For `ai`, `speciality` is required and an SSH keypair + subdomain + workspace are generated; for `direct_quote` (a managed, human-quoted engagement) `speciality` is optional, no AI sandbox is provisioned, `block_auto_development` is set, and there is no charge. For `auto_dev` (§auto_dev, the issue-driven sentinel) `speciality` is required, the `ai` sandbox scaffolding is generated, a connected GitHub/GitLab repo is mandatory (its issues are watched; `other` hosts 400), `issue_watch` must set at least one label or assignee (`authors` is an optional author allowlist), the project is created directly in status `development` (no evaluation/estimate/payment_due - billing is per-run usage), the description is the standing development policy (editable anytime), and no platform GitLab repo is provisioned. For `chat` (§chat kind, "Just chat with me") `speciality` is optional, repos are rejected (400), no sandbox is provisioned and `block_auto_development` is set; the create transaction debits the one-time `CHAT_UPFRONT_CREDITS` opening fee (default 10; 402 if the balance can't cover it, ledger kind `chat_upfront`), the project is created directly in status `development`, and the description is posted as the customer's first main-thread message, which immediately dispatches the first KB-grounded answer. 403 `{"detail": "deposits_paused"}` if an admin has paused new deposits of that `kind` (see `/admin/settings`; chat starts paused - opt-in); admins are exempt.
- `GET /projects/{id}` → `Project`
- `PATCH /projects/{id}` `{name? (1-255 chars), description? (1-40000 chars), git_author_name? (≤120), git_author_email? (≤254)}` → `Project`. At least one field is required (400 otherwise). §git identity: `git_author_name`/`git_author_email` set what the agent's commits in this project are authored as (git `user.name`/`user.email` in the runner) - `""` resets the field to the instance default, and a value carrying a line break or angle brackets is 422 (it would land in `git config`). They apply to the NEXT run; commits already pushed keep the identity they were made with. `description` is only editable while status is `draft` or `awaiting_review`; 409 otherwise (the description locks once the project moves past review). `name` is editable in any status; renaming stops future auto-titling and never changes the demo subdomain (a deployed demo URL never moves).
- `POST /projects/{id}/answers` `{answers: [{question_id, option_ids: [..], comment?}]}` → `{ok}`
- `POST /projects/{id}/evaluate` → `{task_id}` - runs title generation (skipped once the customer has renamed the project) + moderation + feasibility + cost estimate async.
- `GET /projects/{id}/evaluation` → `{state: "pending"|"done"|"failed", moderation?, feasibility?: {verdict: "pass"|"needs_info"|"review_required"|"reject", reasons: [..]}, estimate?: {credits, tokens, cost_per_token, explanation}}`
- `POST /projects/{id}/submit` → `Project` (draft → awaiting_review; requires evaluation pass/review_required)
- `POST /projects/{id}/require-review` → `Project` (→ awaiting_admin, emails admin). Customer-only: 403 for admins (the admin is the reviewer; the SPA disables the button with an explanatory tooltip). On an `ai` project this charges `REVIEW_REQUEST_CREDITS` (120, refundable by admin); 402 if balance too low. Other kinds (`direct_quote`, `auto_dev`, `chat`) are not charged - on a `chat` project this is the human hand-off (the responder stays silent outside `development`).
- `POST /projects/{id}/retry-build` → `Project` - resume development after a build stalled, timed out, or failed. Gated by `dev_can_resume` (an actual failed run, no run in flight, a repo to build into, not blocked, project not `finished`/`canceled`) plus the role rule that `awaiting_admin` resumes are admin-only; 409 with the blocker message otherwise. Optional body `{fresh: true}` (§run chains Start fresh) discards the failed chain instead of resuming it: the abandoned runs are superseded, and the new build starts on a clean workspace and a new (suffixed) branch.
- `POST /projects/{id}/stop-build?run_id=` → `{ok}` - stop the in-flight build (§14). Without `run_id`: only while `dev_run_state` is `running` (409 otherwise; `deploying`/`awaiting_merge` belong to the demo deploy / the customer's merge). With `run_id` (§parallel-builds MR4): the stop is scoped to that sibling run - the mirror gate is skipped and the worker validates the row (belongs to the project, state `running`) before killing anything, no-oping otherwise. The worker kills the sandboxed runner and parks the run as a normal failed, resumable one (`dev_run_error: "Stopped at your request"`), keeping progress already pushed to the branch; `retry-build` resumes it. A stop on a run whose owning worker died (e.g. a platform redeploy mid-run) is honored by the reaper within ~2 of its 60s ticks - the unconsumed stop marker is the ownerless signal - instead of waiting out the full run-timeout window.
- `POST /projects/{id}/approve-delivery` → `Project` - the customer accepts the delivered MVP (awaiting_customer → finished). Requires `ai` kind and a deployed demo (`demo_deployed_once`). 409 otherwise.
- `GET /projects/{id}/dev-logs?run_id=` → `{dev_run_state, dev_run_error, dev_run_started_at, dev_pr_number, dev_pr_url, log}` - last sandboxed dev-run log tail + sub-state, for the build panel / failure diagnosis. `run_id` optional: serves that DevRun ledger row's captured log instead (the request-thread run-history consoles), 404 on a run of another project.
- `GET /projects/{id}/dev-runs?request_id=` → `[{id, request_id, state, created_at, started_at, branch, branch_url, pr_number, pr_url, run_error, security_review, tokens_consumed, cost_credits, has_feed}]` - the development history behind a request's thread (§threads): one DevRun ledger row per run, newest first; `request_id` optional narrows to one request's runs. `state` adds the ledger's own `queued`/`superseded` to the `dev_run_state` values. `has_feed` marks rows whose activity feed `dev-activity?run_id=` can still serve: a parallel-mode run owns its workspace feed, while legacy rows share the project workspace feed, which belongs to the newest started one.
- `GET /projects/{id}/dev-activity?offset=N&run_id=` (run_id optional - §parallel-builds MR2: selects that run's feed, 404 on a run of another project; absent = the primary run at the legacy path, unchanged behavior) → `{state, live, started_at, events: [{ts, kind, title, detail?}], next_offset, reset, usage: ({input_tokens, output_tokens, cached_input_tokens, total_tokens, credits_estimate (number|null), model (string|null)} | null)}` - the §14.8 live build console feed: offset-polled sanitized agent/worker activity events (kinds include `phase|command|edit|read|browse|think|plan|git|scan|usage|error|finish|action|info`) plus the runner's live token snapshot with a display-only credit estimate (billing still happens once per dispatch, from `usage.json`, in the worker). `model` is the api_model the run executes on (from the runner's snapshot - shown per run because project routing can change between runs); `credits_estimate` is null only when the model has no price at all - neither in the static table nor on a saved endpoint - so a project routed to an off-table endpoint model still shows its running cost. Only complete JSONL lines are consumed (a partial tail line waits for the next poll); a missing/replaced feed file (new run) returns `reset: true` or a smaller `next_offset`, telling the client to restart its buffer. Served chunks are platform-secret-redacted, and a line carrying private-key material or a verbatim knowledge-base span is withheld outright. The SPA polls every 2 s while `dev_run_state` is `running`/`deploying` (12 s during `awaiting_merge`).
- `GET /projects/{id}/status-history` → `[{from, to, actor, reason, at}]`
- `GET /projects/{id}/issue-events?limit=20&offset=0` → `{total, events: [{id, kind: "registered"|"deferred"|"paused"|"started"|"unpollable"|"comment_failed", issue_url (string|null), issue_title (string|null), request_id (string|null), detail (string|null), created_at}]}` - §auto_dev only (409 for other kinds): the Issue-watch card's paginated intake history, newest first. One row per sweep decision, never per poll: `registered` (a matching issue became a Request), `deferred` (daily start cap hit - at most one row per issue per UTC day), `paused` (matching issues found on an empty credit balance - throttled with the 24h customer notice), `started` (a build was dispatched for the issue's request), `comment_failed` (the PR/MR-link comment back on the triggering issue failed - e.g. a repository token without issue-write permission, which 403s on comments while pushes and PR opens keep working; one row per failed attempt, `detail` carries the error). `limit` is capped at 100.

Sharing (§sharing). A project can be shared with any registered user by email - the target sees it immediately (dashboard + full project page, incl. the project WebSocket), with no invitation, confirmation, or notification email. Roles: `contributor` (acts as the customer on every project route - chat, requests, builds, demo, memory - billed to the OWNING org's wallet) or `viewer` (read-only: every mutating project route answers 403 `"This project is shared with you read-only"`; the method - POST/PUT/PATCH/DELETE - is the single gate). `admin` is never grantable (it is an instance-wide role). Share management is owner-org (or admin) only - a shared contributor can't manage shares (403):
- `GET /projects/{id}/shares` → `[{id, user_id, email, full_name, role: "contributor"|"viewer", created_at}]`
- `POST /projects/{id}/shares` `{email, role: "contributor"|"viewer"}` → the share (201). Create-or-update: re-posting an already-shared email just changes the role. 404 if no account has this email; 400 for an admin target (they already see everything) or a user of the owning org. Rate-limited `SHARE_RATE_PER_HOUR` per USER (default 20, misses included, 429 past it): the 404-vs-201 answer necessarily confirms whether an email is registered, and the cap is what keeps the route useless as a bulk email-enumeration oracle.
- `DELETE /projects/{id}/shares/{share_id}` → `{ok}` - access ends immediately.

Repos (§multi-repo, `ai`/`auto_dev` projects only; 409 for `direct_quote`/`chat`). A project builds into exactly one **push repo**: a connected repo marked `is_push_target`, else the platform-auto-generated GitLab repo (`platform_repo`, the default). The provider (`github`/`gitlab`/`other`) is detected from the URL host; `other` hosts are buildable (branch pushed over the deploy key, customer merges) but never auto-mergeable.
- `POST /projects/{id}/repos` `{ssh_uri, provider?}` → `Project`. Connect one of the customer's own repos (they add the project deploy key to it). `provider` overrides detection when a self-hosted host is ambiguous. The first connected repo becomes the push target (switching away from the platform repo); 409 if the URL is already connected.
- `PATCH /projects/{id}/repos/{repo_id}` `{is_push_target?, auto_merge?, squash_on_merge?}` → `Project`. `is_push_target: true` makes this the push repo and clears the others (exactly one; all-false ⇒ the platform repo is push). Enabling `auto_merge` re-runs the auth check server-side and is rejected 409 unless it passes; 422 for an `other`-provider repo. `squash_on_merge` (default true, no auth gate) squashes the agent's PR/MR into one commit whenever the platform auto-merges it (falling back to a plain merge when the repo's settings forbid squashing); it is irrelevant when the customer merges manually.
- `POST /projects/{id}/repos/{repo_id}/verify-auth` → `{ok, detail}` - a real authenticated API call confirming the project's `GITHUB_TOKEN`/`GITLAB_TOKEN` is valid AND can access THIS repo (GitHub: `GET /repos/{owner}/{repo}`; GitLab: `GET /projects/:path`). Gates saving `auto_merge`.
- `DELETE /projects/{id}/repos/{repo_id}` → `Project` - disconnect; if it was the push target, the platform repo (or the next connected repo) takes over.
- `POST /projects/{id}/repos/use-platform` → `Project` - make the platform GitLab repo the push target again (clears every connected repo's push flag).

`ProjectSummary = {id, name, kind: "ai"|"direct_quote"|"auto_dev"|"chat", speciality (string|null), status, tier, demo_state, dev_run_state: "idle"|"running"|"awaiting_merge"|"deploying"|"merged"|"failed"|"done" (lets the dashboard animate the status chip while the agent works - running/deploying), access: "owner"|"contributor"|"viewer" (§sharing - the CALLER's access: "owner" for the owning org and admins), created_at}`
`Project = ProjectSummary + {description, from_scratch, sovereign, block_auto_development,
  kb_ids (string[]|null - §KB per-project selection: [] = none, THE DEFAULT for new projects (KBs are opt-in per project); a list = exactly those KnowledgeBase ids; null = all enabled KBs on legacy rows created before the opt-in default; raw ids only, names/kinds stay behind the admin KB API),
  issue_watch ({labels[], assignees[], authors[]}|null - §auto_dev watch filters, null for other kinds),
  gitlab_url (string|null), subdomain, demo_url (string|null, includes the Traefik port off :80/:443),
  demo_basic_auth_user (string|null),
  demo_basic_auth_pass (string|null), demo_state: "stopped"|"running",

Dev pipeline (§14): a project builds into its **push repo** (§multi-repo) - a connected `github.com` or customer GitLab repo, else the platform GitLab repo. The sandboxed agent pushes an `agent/mvp` branch over the project deploy key (this never needs a token). For a customer GitHub/GitLab push repo, what happens next depends on the resolved token - the customer's own `GITHUB_TOKEN`/`GITLAB_TOKEN` Memory secret first, then (GitHub only) the platform-wide `GITHUB_TOKEN` fallback - and the push repo's `auto_merge`:
- **No token (or an `other` host):** no PR/MR is opened (a deploy key can't); the customer opens/merges the branch themselves and `dev_pr_sweep` detects the merge over SSH with the deploy key (`awaiting_merge` → `deploying` → `done`). A normal wait, never a build failure.
- **Token, `auto_merge` off:** a pull request (GitHub) / merge request (customer GitLab) is opened (an empty repo is first seeded with a base `main` branch); the customer reviews and merges it, and `dev_pr_sweep` deploys the demo automatically (`awaiting_merge` → `deploying` → `done`).
- **Token, `auto_merge` on (§14.7):** the PR/MR is opened and its diff is security-reviewed. A clean review (no critical/high finding and no deterministic-floor trip) auto-merges and deploys - squashed into one commit when the push repo's `squash_on_merge` is on (the default); a critical/high finding re-dispatches a scoped fix run (up to `SECURITY_FIX_ATTEMPTS`, re-boot-checked each pass) then re-reviews; exhaustion, or a review that can't run, parks in `awaiting_customer` with the change link for the customer to merge (never a blind merge). The review verdict/findings are on `dev_security_review`. GitHub and customer GitLab share this loop; only the transport differs.

Platform-GitLab projects keep the auto-merge-on-green-CI path (always squashed - the platform repo has no checkbox) and end with the same tail (merge → `deploying` → `done`): every successful run hands off to the demo deploy in `deploying`, and it is the deploy that finalizes the run to `done` (and marks a request-scoped run's request delivered, §12/§14). A post-merge deploy failure (e.g. the canonical-checkout sync) parks the run `merged`, never `failed` - delivered work must not read as a failed build - with the project in `awaiting_admin`; Resume stays disabled ("restart the demo") and the next demo start adopts the newest `merged` row, retries the deploy and finalizes run + request. A run that produces no changes because the request's change is ALREADY merged (a resume of a delivered request) is adopted as delivered (`_adopt_merged_change`), not parked "no changes". Every run is bounded by `DEV_RUN_TIMEOUT_MINUTES` and `DEV_MAX_ITERATIONS` (fail-safe against runaway spend); a failed/timed-out run parks the project in `awaiting_customer` with the log kept, and `retry-build` resumes it. A run whose worker dies mid-build (leaving it stranded at `running`/`deploying`) is recovered to the same resumable state by the `dev_run_reaper` Beat job once it is `DEV_RUN_TIMEOUT_MINUTES + DEV_RUN_REAP_GRACE_MINUTES` past its start, so the API surface (`dev_run_state`, `dev_can_resume`) never hangs in-flight forever. One exception: a platform-GitLab run interrupted *after* the runner already opened its merge request (the runner opens it via a push option during the build) is recovered to `awaiting_merge` instead of failed - the MR is live, so `dev_pr_sweep` merges it on green CI (or the customer's own merge) and deploys, exactly as if the worker had never died. Failing it would strand a customer who then merges the MR to no effect. The customer closes the loop with `approve-delivery` (→ `finished`).

## Chat (immutable)

- `GET /projects/{id}/messages?thread=main` (or `request:<request_id>`) → `[Message]` ascending.
- `POST /projects/{id}/messages` `{thread, body}` → `Message`. A human message in the `main` thread (while the project is in an actionable status) is passed to the §12 chat-intent classifier; the ACTION verdicts additionally require no dev run in flight. It may auto-resume a failed build ("you can continue now"), register a described feature/edit/bug as a `proposed` Request and post an agent ack asking for confirmation before building (the ack carries `meta {kind: "confirm_request", request_id}` rendered as one-click ✓/✗ approve/dismiss buttons - see `Message.meta` below), or - when the ask is actionable but ambiguous - post ONE agent clarifying question with 2-4 one-click options (see `Message.meta` below; the customer answers by clicking an option, which posts its label as a plain message, or by typing free text; at most one question per exchange, never two in a row). A confirmation reply ("go on") - or the ack's ✓ button, which calls `/requests/{id}/start` deterministically - flips the proposed request to `open`, starts its scoped build, and the agent acks in the main thread ("On it - starting …") with a deep link to the request (`/projects/{id}/requests/{request_id}`). Fail-safe/no-op outside those cases (`CHAT_CLASSIFY_ENABLED=0` disables it entirely). A human message in a `request:<id>` thread classifies too, with a reduced action set scoped to THAT request (§threads live threads): confirm its own `proposed` request ("go ahead" in the thread starts the build, acked in the thread), resume the parked run the thread belongs to (the scoped request in flight, or the `mvp` request for a parked MVP build), or answer a question about that request's work; every other verdict is silently dropped - requests are filed and clarified from `main`, and an inert thread reply still reaches the next run through the §resume steering transcript. **Work answers (§work answers):** a question about the project's own work - what a build did, where it stands, what it cost - gets an async agent answer posted in the thread it was asked in (`meta` `{answers: <message_id>}`), grounded in the project's own record (requests, the summary each run published, the push repo's commit subjects + touched files, the build-feed tail, Memory names) and billed as ordinary project consumption. A message containing `@agent` or `@ai` is guaranteed a reply: an action verdict still wins (its ack is the reply), anything else - including an LLM outage - answers. Answering is allowed WHILE a build runs (it only reads); the action verdicts are not. Guards: one 24h-throttled notice on an empty wallet or an unpriced model, `WORK_ANSWER_RATE_PER_10MIN` per-org cap (default 12), `WORK_ANSWER_ENABLED=0` kill switch. EXCEPTION - `chat` projects (§chat kind): the classifier never runs; instead every CUSTOMER main-thread message (while the project is in `development`) gets an async KB-grounded agent answer (retrieval over the project's KB selection + Memory- and history-aware synthesis, verbatim-guarded like the MCP knowledge path, `Sources:` refs appended when passages were cited), billed to the project as ordinary consumption. The answer arrives over the WS/polling merge; its `meta` is `{answers: <message_id>}` (dedup marker). Guards: one 24h-throttled agent notice on an empty wallet, `CHAT_ANSWER_RATE_PER_10MIN` per-org cap (default 20), `CHAT_ANSWER_ENABLED=0` kill switch; outside `development` (human hand-off, finished) the responder stays silent.
- `POST /projects/{id}/request-human-answer` `{thread}` → `{ok}` - the customer explicitly pulls the consultant into the thread (replaces the classifier auto-defer): posts an agent confirmation message, moves the project to `awaiting_admin` (free of charge), and emails the admin (directly when the project is already `awaiting_admin`). 409 when the transition isn't allowed (canceled).
`Message = {id, thread, author: "customer"|"admin"|"agent"|"system", body, meta, emailed: bool, created_at}` - `meta` is platform-authored and null except on an agent clarifying question, where it is `{kind: "question", question, options: [{label, description|null}], allow_free_text: true}` (the shared-ui `QuestionPrompt` renders it), on the §12 request-proposal ack ("I read this as a … request") and the still-holding nudge, where it is `{kind: "confirm_request", request_id}` (the shared-ui `ConfirmPrompt` renders ✓ Go ahead / ✕ Not now buttons wired to the deterministic `/requests/{id}/start` and `/cancel` actions - no classifier round-trip; the panel freezes on the next human main-thread reply, highlighting the outcome when it matches the canned "Go ahead"/"Not now" those actions post), on a §chat-kind agent answer, where it is `{answers: <customer message id>}` (dedup marker, no UI meaning), and on any agent message referencing a PR/MR, where it carries `{prs: [{number, url, provider: "github"|"gitlab"}]}` (§PR chips - the shared-ui `PrChips` renders each as a clickable chip and strips the raw URL from the body text). `MessageIn` accepts no meta, so a client can never post one.
- WebSocket `GET /ws/projects/{id}` (cookie-authed). Server pushes JSON events:
  `{type: "message", message: Message}`, `{type: "status", status, project_id}`, and `{type: "dev", dev_run_state, project_id}` (published on every dev_run_state change, so the Development panel picks up a run it isn't polling for yet - e.g. a request build starting. The payload carries the new state: it can arrive milliseconds before the worker's commit, so consumers apply it directly and refetch shortly after).

## Requests

- `GET /projects/{id}/requests` → `[Request]`
- `POST /projects/{id}/requests` `{type: "feature"|"edit"|"bug"|"production_deploy", handling: "ai"|"manual", body}`
  → `Request` (creates its thread with the body as first message; production_deploy forces handling=manual). There is no `title` input: a bootstrap title is derived from the body at creation and the async `title_request` task refines it with the LLM title prompt - unless the title was edited in the meantime (compare-and-set on the bootstrap value; an edit always wins).
- `PATCH /projects/{id}/requests/{request_id}` `{title (1-255 chars)}` → `Request` - rename a request (any status; also stops the pending auto-title pass from applying).
- `POST /projects/{id}/requests/{request_id}/start` → `Request` - start an AI-handled request the agent proposed from chat (`proposed` → dispatches the scoped dev job via `handle_request`, which gates on credits / buildable / no run in flight). The Requests-tab counterpart to replying "go ahead" in the thread; customer or admin. 409 if the request isn't AI-handled, has already been started, or is the `mvp` request (the initial build is driven from the overview's Resume-development action); 404 if unknown.
- `POST /projects/{id}/requests/{rid}/validate` → request - §requests: the customer (or admin) marks an AI-handled request DELIVERED by hand, the per-request twin of approve-delivery and the escape hatch for work that landed while the pipeline reported failure (e.g. a run that pushed onto an already-open PR and exited non-zero). Guards: 409 for the mvp request (approve-delivery owns it), manual/production_deploy handling, an already done/rejected request, or a run for it still queued/running/deploying (stop first - validation never kills a live build). Effects: request `done`; an awaiting_merge run of its closes (state `done`, the merge sweep stops watching); the `Project.dev_*` mirror repoints at the newest still-active sibling, else settles on `done`; a system message lands in the request thread. Hub pass-through: `POST /hub/projects/{id}/requests/{rid}/validate` (acts as the customer).
- `POST /projects/{id}/requests/{rid}/cancel` → request - §requests: the negative twin of validate. Same guards (mvp / manual / production_deploy / already closed / live build 409 - stop first). Effects: request `rejected`; an awaiting_merge run of its parks `failed` ("Request canceled"); when the mirror pointed at it and no sibling is active, the work unit ends the way dev_pr_sweep ends rejected work - branch/PR pointers cleared, `dev_run_state` settled `idle` (console retracts; an open PR left on the repo is the customer's to close). Hub pass-through: `POST /hub/projects/{id}/requests/{rid}/cancel`.
- §repo binding intent: `POST /projects/{id}/requests` (and the hub twin) accepts optional `repo_id` - the connected repo this request's builds push into (404 for a foreign/unknown id; null = the project's default push target at dispatch time). The request payload serializes `repo_id`; chat-filed requests infer it deterministically when the message's URLs unambiguously name one connected repo, and auto_dev issue requests bind to the watched repo. A request pinned to a NON-default repo is a PULL-REQUEST deliverable: no demo boot gate, no demo redeploy on merge - the merge completes the request (auto_dev semantics).
- `POST /projects/{id}/requests/estimate` (same body) → 202 `{task_id}` - async, informational cost/time estimate for a request being drafted (never a quote). The project's own LLM is anchored on averages of past completed dev runs that used the same model; the call is metered like any other.
- `GET /projects/{id}/requests/estimate/{task_id}` → `{state: "pending"|"failed"|"done", estimate?: {available, cost_credits?, time_hours?, explanation?, reason?, based_on?: {runs, model}}}`. `available: false` when there is no history for the model or the model declines/fails (`reason`: `no_history` | `model_declined` | `llm_unavailable`).
`Request = {id, project_id, type ("mvp"|"feature"|"edit"|"bug"|"production_deploy" - `mvp` is Request #0, the server-created initial-build request anchoring the MVP build's thread; never accepted from clients), handling, status: "proposed"|"open"|"quoted"|"in_progress"|"done"|"rejected", title, price_credits, tokens_consumed: int, cost_credits: number, source_issue_url (string|null - §auto_dev: the repo issue this request was auto-created from), pr_urls ([{number, url, provider: "github"|"gitlab"}] - §PR chips: every PR/MR this request's dev runs opened, oldest first, dedup by url across re-runs; [] when none), created_at}` - A terminal project transition closes its `mvp` request automatically (`finished` → `done`, `canceled` → `rejected`; already-closed rows are left alone, and other request types are never touched), so a closed project never keeps Request #0 open. - `proposed` is an agent-proposed request from chat awaiting the customer's go-ahead (start it via `/requests/{id}/start` or by confirming in chat); it becomes `open`/`in_progress` once started. - `tokens_consumed`/`cost_credits` are the LLM usage attributed to this request's thread (its scoped dev runs), a per-request view of the project totals.

A request whose task is an INVESTIGATION closes without a PR (§investigation runs): when the run's honest outcome is "nothing to change", the agent writes its findings to `.openvisor/report.md`, the platform posts them into the request thread as the answer and the request goes straight to `done` - no `pr_urls`, nothing to merge. A run that produced nothing AND wrote no report is still a failure, resumable as before.

AI-handled feature/edit/bug requests spawn a scoped dev job (§14) when the project is buildable (MVP shipped, credits > 0, not blocked, no run in flight): request → `in_progress`, the agent builds only that change and opens a PR titled after the request, and once the customer merges it the demo redeploys and the request → `done`. When the job can't start, the agent explains why and points at the Request-human-answer button. Failed request runs on an open project are resumable via `retry-build`; on a `finished` project the button is disabled (closed projects never resume - the customer submits a new request instead, or the admin reopens via `development`). `manual` requests notify the admin directly (quote path).

## Routines (§routines)

A routine is a SAVED PROMPT on a project, optionally scheduled. It is a template, not a run: every firing creates an ordinary `Request` seeded with the prompt and dispatches it down the normal pipeline, so one routine owns many requests over time (the Program → ProgramRun shape). Available on any project that builds (`ai` and `auto_dev`); `chat` projects have no build pipeline and no tab.

- `GET /projects/{id}/routines` → `[Routine]` (oldest first).
- `POST /projects/{id}/routines` `{title, prompt, enabled?, schedule_cron?, repo_id?}` → `Routine`. An empty `schedule_cron` means hand-fired only; a set one is validated by croniter against the `ROUTINE_MIN_SCHEDULE_MINUTES` floor (default 60 - a routine starts a real dev run, so the floor is higher than the program one) and 400s below it. `repo_id` must be a repo connected to this project (§repo binding); null resolves the push target at fire time.
- `PUT /projects/{id}/routines/{routine_id}` - partial update, same validation. `next_run_at` is recomputed on every write: a scheduled AND enabled routine always has one, anything else has none (so pausing or clearing the cron stops it immediately).
- `DELETE /projects/{id}/routines/{routine_id}` → `{ok}` - deletes the routine; the requests it already spawned are history and stay.
- `POST /projects/{id}/routines/{routine_id}/run` → `Routine` - fire now. Ignores the schedule but NOT the guards (same `routines.fire` the sweep calls), so it 409s with the same copy the sweep would have recorded.

`Routine = {id, project_id, title, prompt, enabled, schedule_cron, next_run_at, last_run_at, last_request_id, last_request_status, last_skip_reason, repo_id, created_at}`

Firing guards (all 409 on "Run now", all recorded in `last_skip_reason` on a scheduled tick, which then moves `next_run_at` on): the routine is paused, the project is canceled/finished or has automatic development blocked, the org wallet is empty, a build already holds the project's slot, or - the one specific to routines - **the previous request is still open**. Unlike the auto_dev sweep, a routine has no dedup key (running the same prompt every Monday IS the feature), so that last guard is what stops a weekly routine stacking a second build on an unmerged PR.

Instance switch: `routines_disabled` (admin settings) hides the tab via `GET /settings.routines_enabled` and makes every routine write 403. Existing routines are kept and simply stop firing, so re-enabling resumes them.

## Programs (§28)

A Program is an admin-managed repo in the platform GitLab executed as `docker compose build && docker compose run program` in a throwaway DinD sandbox; customers instantiate published programs from the catalog and never see the repo itself.

- `GET /programs?q=` → `[ProgramBrief]` - published catalog; `q` matches the title or the short description (admins also see unpublished programs).
- `GET /programs/{id}` → `Program` (adds `readme_md` and the `input_template` the inputs form is generated from).
- `POST /programs/{id}/instances` `{label?}` → `ProgramInstance` - adds the program to the caller's org (several instances of one program per org are allowed) and generates the per-instance SSH keypair whose private key is mounted into the program container as a compose secret.
- `GET /program-instances` → `[ProgramInstance]` (own org; admins see all).
- `GET /program-instances/{id}` → `ProgramInstance`.
- `GET /program-model-endpoints` → `[{id, label, model_name}]` - the saved model endpoints an instance may be pinned to (§28 per-instance model), sorted by label. Any authenticated user; endpoints saved without a model are omitted (nothing could resolve through them), and the base URL, the key and the prices are never exposed.
- `PUT /program-instances/{id}` `{label?, inputs?, model_endpoint_id?, webhook_url?, schedule_enabled?, schedule_cron?, hook_enabled?, hook_filters?}` → `ProgramInstance`. `model_endpoint_id` pins which model this instance runs on: an id from `GET /program-model-endpoints` (404 for an unknown or model-less one), `""` clears it back to the program's admin-set default, absent leaves it unchanged. `hook_filters` = `{actions[], labels[], assignees[], authors[]}` AND-composed allowlists for the inbound trigger hook (§28: empty list = no constraint); enabling `hook_enabled` on a pre-hook instance lazily generates the secret. `inputs` replaces the whole value map and is validated against the template: 422 `{"detail": {"message", "errors": {field: msg}}}` names exactly which input is wrong. `webhook_url` must be http(s) and, outside local dev, must not resolve to a private address (400). `schedule_cron` is croniter-validated with a `PROGRAM_MIN_SCHEDULE_MINUTES` floor (default 15; 400 below it); enabling the schedule requires the program to be `schedulable` and recomputes `next_run_at`.
- `DELETE /program-instances/{id}` → `{ok}` - 409 while a run is in flight; deletes the rows and reclaims the sandbox, its layer-cache volume and the artifact dir async.
- `POST /program-instances/{id}/run` → `ProgramRun` (state `queued`) - manual trigger. 409 when a run is already queued/running (one run per instance at a time), 402 on an empty wallet, 422 on invalid inputs.
- `POST /program-instances/{id}/hook-secret` → `{hook_secret}` - rotates the inbound-hook secret (previously configured webhooks stop verifying immediately).
- `POST /programs/hooks/{instance_id}` - the PUBLIC inbound trigger receiver (§28, CSRF-free; the signature is the auth). Verifies GitHub `X-Hub-Signature-256` (HMAC-SHA256 of the raw body) or GitLab `X-Gitlab-Token` (constant-time equality) against the instance's `hook_secret`; 404 for unknown/disabled instances, 401 on a bad signature, 413 over 1 MB, 429 over the per-instance rate cap (`PROGRAM_HOOK_RATE_PER_MINUTE`, default 30). Replays dedup on the provider delivery id (`X-GitHub-Delivery`/`X-Gitlab-Event-UUID`, 24 h redis window). Issue events matching `hook_filters` enqueue a `ProgramRun` kind `hook` carrying the normalized event (staged as `input/event.json` in the sandbox); everything else - non-issue events, filter misses, duplicates, a full pending queue (`PROGRAM_HOOK_MAX_PENDING`, default 5) - is acknowledged 204 without a run so the provider never retries a deliberate drop. An empty wallet records a visible `failed` run instead of running.
- `GET /program-instances/{id}/runs?limit=50` → `[ProgramRun]` (newest first, limit ≤ 200).
- `GET /program-instances/{id}/runs/{run_id}` → `ProgramRun + {output_text, output_files: [{path, size}], log_tail}` - `output_text` is output/output.txt (≤256 KB).
- `GET /program-instances/{id}/runs/{run_id}/log?offset=0` → `{content, next_offset, done}` - offset-poll this for live logs (the deployer streams the sandbox log to the shared workspaces volume as the run executes). Platform secret values are redacted from served content; a `blocked` run returns the withheld-findings summary instead of the raw log.
- `GET /program-instances/{id}/runs/{run_id}/files/{path}` → download of one output/ file (Content-Disposition attachment, traversal-guarded). 403 on `blocked` runs; 404 once an old run's artifacts were pruned (`PROGRAM_RUN_RETENTION` dirs kept per instance, default 20 - DB rows keep `output_text`/`log_tail` so history stays readable).

`ProgramBrief = {id, title, short_description, schedulable, is_published, created_at}`
`Program = ProgramBrief + {readme_md, input_template: [{name, label, description, type: "text"|"multiline"|"number"|"boolean"|"choice", required, default, secret, placeholder, options}]}`
`ProgramInstance = {id, program: Program, label, inputs: {name: value}, model_endpoint_id (string|null - null = the program's default model), webhook_url, hook_enabled, hook_url, hook_secret (string|null), hook_filters: {actions[], labels[], assignees[], authors[]}, schedule_enabled, schedule_cron, next_run_at, ssh_public_key, created_at, latest_run: ProgramRun|null}` - input values return in clear (encrypted at rest; a template field's `secret` flag masks display only, Memory parity).
`ProgramRun = {id, instance_id, kind: "manual"|"schedule"|"check"|"hook", state: "queued"|"running"|"succeeded"|"failed"|"timeout"|"blocked", exit_code, error, tokens_input, tokens_output, cost_credits, webhook_status, created_at, started_at, finished_at}`

Billing: the program writes `.openvisor/usage.json` `{model, input_tokens, output_tokens, cached_input_tokens?}` (dev-runner contract; the optional field = provider prompt-cache reads, billed at the model's cached rate - report the `OPENAI_MODEL` value verbatim, which is the instance's pinned model when it has one) and the worker bills it against the org wallet at the PROGRAM's markup (`CreditTransaction kind="program_run"`, project-less). A run that writes no report bills nothing. A scheduled tick with an empty wallet records one failed run ("insufficient credits") and disables the schedule; manual runs 402.

Webhook: at the end of EVERY run the platform POSTs `{run_id, instance_id, instance_label, program: {id, title}, kind, state, exit_code, error, started_at, finished_at, credits_charged, output}` to `webhook_url` (10s timeout, 3 attempts with backoff; `webhook_status` records `delivered`/`failed`). `output` is the output.txt text, null when the run produced none or was blocked.

Protections: before output/log become visible or the webhook fires, the worker scans the output files and the run log for verbatim platform secrets and knowledge-base spans (leak-scan parity with the dev pipeline); a hit sets state `blocked`, withholds output and log, and emails the admin. Timeouts (`Program.timeout_minutes`, default 15) kill the sandbox and end the run in state `timeout`.

## Knowledge (MCP `search_knowledge`, Bearer PROJECT-scoped `ov_` token - no session/CSRF)

- `POST /knowledge/answer` `{query (1-2000 chars), k?: 1-12 = 6}` → `{answer, citations: [{n, source, ref}], credits_charged}`. Auth is the `ov_` API token via `Authorization: Bearer` (not the session cookie), and it MUST be **project-scoped**: the project chooses the synthesis model (`services/model_config.project_model_config` - the same resolution its chat and dev runs use), narrows retrieval to its own `kb_ids` selection, and is what the query bills to (a project `consumption` row plus the project's token/credit counters). An account-wide token has none of those, so it gets `403` with a message pointing at project tokens. Synthesizes a cited answer from the KB (retrieved via Meilisearch hybrid search) and meters the query-embedding + synthesis model cost (× `CREDIT_MARKUP`); Meilisearch ranks the passages natively, so no reranker model is billed. Never returns raw KB chunk bodies (citations are references only; verbatim spans are redacted). `402` `{"detail": "Insufficient credits. Top up at …/billing"}` when the wallet is empty; `503` when the knowledge models aren't priced or the LLM is unavailable; per-org rate limit `429`. The `mcp.<domain>/mcp` server's `search_knowledge` tool proxies to this endpoint.

## Hub (Bearer hub `ov_` token - no session/CSRF)

Control surface for a central Scalevisor Hub; every endpoint requires a hub-scoped token (`POST /admin/hub-token`) and rejects user-scoped tokens with `403`. Mirrored as MCP hub tools on `mcp.<domain>/mcp` (`spoke_info`, `usage_summary`, `list_credit_events`, `find_org`, `create_org`, `grant_credits`, `kb_leak_audit`, `run_eval`, and the §pass-through project tools `create_project` / `get_project` / `get_project_evaluation` / `list_project_messages` / `get_project_dev_activity` / `project_action`). Optional: with `HUB_MCP_URL` unset the spoke never calls a hub, but this inbound surface is always available to a hub token.

Privacy boundary: per-org data (`/usage`, `/credit-events`) is scoped to **hub-relevant orgs** - orgs the hub created (`hub_managed`) or has ever funded (a `HubCreditGrant` row) - so a hub token can never read the spoke owner's direct-customer business; the outbound `hub_usage_report` Beat job streams the same scoped set. The project surface has a second hard boundary: every `/hub/projects/*` route 404s unless the project is `source='hub'`, so direct-customer projects are invisible to a hub token, and an optional `?org_id=` (the hub derives it server-side from its own org link) turns a hub-side authz bug into a `403` instead of a cross-customer read. Every endpoint is rate-limited per hub token (reads share a 240/60s budget; `orgs/find` and `POST /orgs` 30/600s; `credits/grant` and the project writes 60/600s; `kb-audit` 6/600s; `eval` 10/600s) as the runaway/stolen-token backstop; over-limit → `429`.

- `GET /hub/info` → `{deploy_domain, credit_currency, org_count, project_count, version}` - brand-agnostic spoke identity (counts are spoke-wide aggregates).
- `GET /hub/usage?since=` → `{by_kind: {kind: net_amount}, net, cursor}` - `credit_transaction` rollup over hub-relevant orgs grouped by kind, optionally after an ISO-8601 `since`; `cursor` is the newest `created_at` seen.
- `GET /hub/credit-events?since=` → `{events: [{id, org_id, project_id, amount, kind, detail, created_at}], cursor}` - raw ledger feed over hub-relevant orgs after `since`, oldest first, ≤500 rows/page; poll again with `since=cursor`.
- `GET /hub/orgs/find?email=` → `{org_id, org_name}` (`404` if no user has that email). Only for linking an EXISTING direct customer who asked the hub to fund them; brokered hub customers use `POST /orgs`.
- `POST /hub/orgs` `{name, idempotency_key (≥8 chars)}` → `201 {already_created, org_id, org_name, credit_balance}` - creates a brokered, hub-managed org for one of the HUB's customers (§hub pass-through). No spoke `User` is created (the customer never logs in here, so the spoke sends them no email). Idempotent on `idempotency_key`: a replayed create returns the existing org with `already_created: true` and writes nothing. The name is hub-chosen - a neutral alias in anonymous mode, never customer PII by contract.
- `POST /hub/credits/grant` `{org_id, amount, idempotency_key, detail?}` → `{already_applied, grant_id, org_id, amount, credit_balance}`. `amount` must be `0 < amount ≤ HUB_MAX_GRANT_CREDITS` (`400` otherwise), and when `HUB_MAX_DAILY_GRANT_CREDITS > 0` the rolling-24h grant total may not exceed it (`429` - the backstop against a stolen token minting credits in a loop of fresh keys); the balance moves via an atomic UPDATE and a `CreditTransaction kind="hub_grant"` (project-less). Idempotent on `idempotency_key`: replaying a key returns the original grant with `already_applied: true` and writes nothing. A fresh grant re-checks `payment_due` projects the top-up may now cover. `404` if the org is unknown.
- `POST /hub/kb-audit` (no body) → `{risk_score: 0..1, level: "low"|"medium"|"high", checked_at, probe_count, leaked_count, findings: [{probe, category, leaked, max_overlap_words}]}`. Report-only KB-confidentiality self-audit: red-teams the spoke's own `search_knowledge` retrieval+synthesis path with a battery of adversarial extraction probes (`direct-exfil`, `prompt-injection`, `context-dump`, `topic-sweep`) and flags a probe as leaked when its final answer's longest verbatim KB word-run reaches the live guard's threshold (`knowledge.MIN_VERBATIM_RUN`, ~12). `risk_score` is the category-weighted leaked fraction (exfil/injection weighted above sweeps); levels: low `<0.15`, medium `<0.4`, high `≥0.4`. Bills nothing, requires no credits, and NEVER returns KB text, chunks or synthesized answers - only scores/flags (sending KB text to the hub would itself be the leak). Runs the sync RAG/LLM stack in a threadpool, bounded well under 120s; if that stack is unavailable it returns `level: "unknown"` plus an `error` note instead of raising (the hub treats `unknown` as a soft failure).
- `POST /hub/eval` `{questions: [str] (1-4, each ≤2000 chars), k?: 1-12 (default 6)}` → `{answers: [{question, answer, matched}], count}`. Runs each owner-consented eval question through this spoke's knowledge stack (retrieval → synthesis → verbatim guard), UNBILLED, and returns the guarded answer text - the same guard `search_knowledge` applies, so no raw KB text can leak. `matched` is `false` with `answer: ""` when retrieval finds nothing (no LLM call). A single question's internal failure soft-fails just that answer (`answer: ""`, `matched: false`, `error: "unavailable"`) without failing the batch. Rate-limited per hub token (10/600s) so a runaway hub can't burn the owner's LLM budget. Runs the sync RAG/LLM battery in a threadpool.

From-hub projects (§pass-through P1) - the hub drives a brokered customer's project lifecycle through these; every route takes an optional `?org_id=` defense-in-depth check (above):

- `POST /hub/projects` `{spoke_org_id, kind? (ai|direct_quote|chat, default ai), speciality?, description, from_scratch?, sovereign?, sovereign_comment?, hub_ref?, repos? ([{ssh_uri}], max 5, `ai` only), auto_merge?}` → `201 Project` (the same `project_out` shape as the customer API, demo creds included). Only into `hub_managed` orgs (`403` otherwise); the deposit-pause gate re-runs server-side exactly as for customers (`403 deposits_paused`). Mirrors the customer create (name bootstrap, SSH key, workspace, demo creds, async provisioning) with two anonymity differences: the subdomain is OPAQUE (`<uuid-prefix>-project`, never name-derived - and the evaluation retitle keeps it), and provisioning passes no email so no spoke GitLab user is ever created. Connected repos (§hub shared repo): `repos` binds SSH remotes exactly as the customer create does - the first is the push target, the provider is host-detected, and a push-target repo SKIPS platform-GitLab provisioning (the connected repo is where the work lives; the workspace mkdir still runs). SSH remotes only (`400` otherwise); `from_scratch=false` requires at least one repo. `auto_merge` pre-arms the platform-merge flow on the push repo - it only actually merges when a valid `GITLAB_TOKEN`/`GITHUB_TOKEN` Memory secret is present at merge time (the hub feeds one per project via `PUT /hub/projects/{id}/memory`), else the flow degrades to the customer-merge path. - `GET /hub/projects/{id}` → `Project` (`project_out`, `404` unless `source='hub'`).
- `POST /hub/projects/{id}/repos/check` → `{ok, detail}` - SSH reachability of the push-target repo over the project's own deploy key (the customer verify-ssh check, hub-scoped; a project with no connected push target answers ok=false with a managed-repo note). The hub runs it before funding work into a customer-provided repository.
- `GET /hub/projects/{id}/evaluation` → the §7 evaluation payload (`{state: "none"}` before the first run).
- `GET /hub/projects/{id}/messages?thread=` → same contract as the customer `GET /messages` (thread `main` | `request:<id>`, full ordered list) so the shared UI's ProjectApi stays single-shaped.
- `GET /hub/projects/{id}/dev-activity?offset=` → same offset-poll contract as the customer build console; devfeed redaction applies unchanged.
- `POST /hub/projects/{id}/actions` `{action: "evaluate"|"submit"|"approve-delivery"|"retry-build"|"stop-build"|"require-admin"|"demo-start"|"demo-stop"}` → `evaluate` returns `{ok, task_id}`; the rest return `{ok, project}`. All wrap the SAME `services/project_actions` functions the SPA routes use (guards can't drift; the hub always acts as the customer, so `retry-build` keeps the awaiting_admin block and `require-admin` charges the org wallet; `demo-start`/`demo-stop` wrap the SPA demo routes' guards - deployable statuses only / running only); `ActionError` maps to its HTTP status.
- `POST /hub/projects/{id}/messages` `{thread?, body}` → `201 Message` - posts as the customer; the §12 classifier and side effects run exactly as for the SPA.
- `GET /hub/projects/{id}/requests` / `POST` `{type, handling?, body}` / `POST .../requests/{rid}/start` - the Requests surface, contract-identical to the customer API (AI-handled requests spawn the scoped dev job; production_deploy routes to a manual admin quote).

Event outbox (spoke→hub): every status/message/evaluation/demo event on a `source='hub'` project is written to `hub_project_event` in the SAME db transaction as the state it mirrors, and the `hub_project_events_report` Beat job (60 s) pushes unsent rows to the hub's `report_project_events` MCP tool claim-based (`sent_at IS NULL` + `FOR UPDATE SKIP LOCKED`, marked sent only on a full ack) - at-least-once, hub dedups on the row id.

- `PUT /admin/projects/{id}/model-config` `{endpoint_id}` → `{ok}` - selects a saved model endpoint for this project (the model + credentials come from the endpoint; `endpoint_id` null clears the override → global default). `GET` returns `{endpoint_id}`.
- `GET/POST/PATCH/DELETE /admin/model-endpoints[/{id}]` - the instance-wide saved-model-endpoint library. Body `{label, provider(openai|anthropic|mistral|openrouter|eurouter|carouter|custom), base_url, api_key, model_name, input_price?, output_price?}` - `provider` is a preset hint (it picks the auth header shape and prefills the base URL in the admin form), not a capability claim; the three routers are OpenAI-compatible gateways, and a gateway model id (`vendor/model`) is usually absent from the static price table, so it needs the explicit prices below; the API key is envelope-encrypted and never returned (only `has_api_key`). `model_name` in the static price table needs no price; a model NOT in it must supply `input_price`+`output_price` per 1M tokens (400 otherwise), which billing then uses. Response adds `model_priced` (bool). DELETE returns 409 while a project still references the endpoint.
- `POST /admin/model-endpoints/models` `{provider, base_url, api_key?, endpoint_id?}` → `{models: [{id, priced}], error}` - the provider's live model list for the endpoint form's picker (`GET {base_url}/models`; Anthropic via `x-api-key`, others Bearer; the key is the one supplied, else the referenced endpoint's stored key). Upstream failures soft-fail to `models: []` + `error` (the form falls back to a custom model name); obvious non-chat families (embeddings, audio, image…) are filtered out.
- `GET /admin/model-endpoints/priced-models` → `{models: [api_model…]}` - every model the static price table can bill (the form hides the price inputs for these).
- `POST /admin/model-endpoints/{id}/test` → `{chat_completions: {ok, status, error}, responses: {…}|null}` - 1-token preflight of the API surfaces a dev run hits: `/chat/completions` always, `/responses` for OpenAI gpt-5/codex-family models. Informative only, never blocks saving.
- `POST /projects/{id}/messages` with extra field `{also_email: true}` - admin only; emails the message.
- `POST /admin/requests/{req_id}/price` `{price_credits}` → `Request`
- `POST /admin/requests/{req_id}/quote` `{amount}` → quote + Stripe payment link (may 503 locally)
- `POST /admin/projects/{id}/quote` `{amount}` → project-level quote + Stripe payment link (used for `direct_quote` projects)
- `POST /admin/projects/{id}/quotes` `{title, details, price_credits}` → `Quote` - credit quote for the Quotes tab (status `sent`; posts a system chat message).
- `PATCH /admin/quotes/{quote_id}` `{title?, details?, price_credits?}` → `Quote` - title/details editable at any time; price locked once accepted/denied/canceled (409).
- `POST /admin/quotes/{quote_id}/cancel` `{comment?, refund_credits?}` → `Quote` - withdraw a credit quote the admin won't deliver (allowed from `sent` or `accepted`; 409 otherwise). On an accepted (paid) quote, `refund_credits` (0 up to `price_credits`, 400 outside) is returned to the org wallet as ledger kind `refund`; on a `sent` quote a refund is rejected (409, nothing was paid). Posts a system chat message and emails the customer.
- `POST /admin/quotes/{quote_id}/attachments` multipart `files[]` (≤15 MB each) → `[{id, filename, content_type, size_bytes}]`
- `DELETE /admin/quotes/{quote_id}/attachments/{attachment_id}` → `{ok}`
- `GET /admin/projects/{id}/spend` → `{credits_spent, by_kind: {kind: net_amount}, quotes_paid, total_spent}` - what the customer spent on the project (net project-scoped credit ledger + Stripe-paid quotes; EUR≈credits parity for the alpha). Ledger amounts are signed (debits negative).
- `POST /admin/projects/{id}/refund-review` → `{credit_balance, refunded}` - refund the review-request fee (409 if already refunded, 404 if none)
- `POST /admin/orgs/{org_id}/credits` `{amount, reason}` → `{credit_balance}` (manual adjust/topup)
- `POST /admin/hub-token` → `{id, name, scope, token}` - mint a hub-scoped API token (plaintext once) authenticating a central hub to `/api/hub/*`. A hub token can read usage and grant credits but never bills a knowledge query.
- `GET /admin/users` → `[{id, email, role, org_id, org_name, email_verified, blocked, created_at}]`
- `PATCH /admin/users/{id}` `{blocked?}` → `{id, blocked}` - §user blocking: flip a user's lockout (applied only when the field is sent). 404 unknown user; 403 `"Admin accounts cannot be blocked"` for admin targets.
