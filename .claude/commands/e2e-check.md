# Openvisor E2E workflow check

Act as both the customer and the consultant (the admin) to verify the full customer↔consultant workflow end to end on THIS instance. Read the instance identity from `.env` first (`COMPOSE_PROJECT_NAME`, `DEPLOY_DOMAIN`, `TRAEFIK_HTTP_PORT`, `POSTGRES_DEV_PORT`) and derive the URLs from it - e.g. instance 2 is app `http://app.openvisor2.local:8090`, mailpit `http://mail.openvisor2.local:8090`, postgres `127.0.0.1:5434`. Admin login is in "Users for test" above. Use Chrome MCP for all UI steps. NEVER touch the other instance's checkout, containers, ports, or database. Wildcard DNS `*.openvisor.local` / `*.openvisor2.local` → 127.0.0.1 is configured on this machine, so demo URLs open in the browser.

0. **Prep** - check the stack is healthy (`docker compose -f compose.base.yml -f compose.dev.yml ps`). Reset the GitHub test repo (a test repo you own, e.g. `youruser/openvisor-demo-todo`) with the gh CLI: close open PRs and delete the `agent/mvp` branch (keep `main`). Default to `OPENHANDS_ENABLED=0` (the deterministic scaffold goes through the exact same push→PR→merge→deploy pipeline, zero LLM tokens); only use `=1` if I explicitly ask for a real-agent run, keeping the `DEV_RUN_TIMEOUT_MINUTES` / `DEV_MAX_ITERATIONS` caps in place. Restart worker+beat after any `.env` change.
1. **Customer signup** - create `e2e+<timestamp>@example.com` through the signup UI in an isolated browser context (solve the ALTCHA - on the sign-in form too, §captcha; if the widget wedges, solve the PoW and POST `/api/auth/signup` and `/api/auth/login` directly, one fresh challenge per call), verify the email via the mailpit link, log in.
2. **Project creation (customer)** - new AI project "TodoApp E2E <date>" (web/SaaS speciality, existing repo - a test repo you own, e.g. `git@github.com:youruser/openvisor-demo-todo.git` - not from scratch), answer the onboarding questions, run evaluation, submit for review. Then add the project's NEW `ssh_public_key` (shown on the project page) as a WRITE deploy key on the repo with gh (`gh repo deploy-key add --allow-write`), removing stale deploy keys from previous runs first.
3. **Memory / Requests / chat (customer)** - add `SUPABASE_URL` (plain) and `SUPABASE_ANON_KEY` (secret - must render as ••••••), create one feature Request, send one main-thread chat message (no automatic agent reply: an agent bubble must offer "Request human answer" - click it and expect awaiting_admin + an admin email per §12).
4. **Consultant review (admin)** - if evaluation is `review_required`, clear `block_auto_development`; move the project to `payment_due` with a note; verify the customer received the payment_due email in mailpit.
5. **Payment** - try the real Stripe sandbox topup (webhook route is `/api/billing/stripe/webhook`; a `stripe listen` must forward there). If the round-trip doesn't credit within a few minutes, don't burn time on it: grant credits via `POST /api/admin/orgs/{org_id}/credits` and note the fallback. Verify the auto-advance `payment_due` → `development`.
6. **Dev pipeline (GitHub PRs)** - `run_development` must push `agent/mvp` to the customer repo and open a PR (an empty repo gets its `main` branch seeded first); the project lands in `awaiting_customer` with `dev_run_state=awaiting_merge` and the PR link visible on the project page.
7. **PR merge (customer)** - review and merge the PR with gh (`gh pr merge --merge`); within ~60 s the `dev_pr_sweep` Beat job must deploy the demo (`demo_state=running`). Open the demo URL with its basic-auth creds and confirm the app renders.
8. **Fail-safe spot-check** - exercise Resume development once and confirm the Development panel (state badge, PR link, View logs with the run log, error message on failure) and the status-history entries. Optionally test the trial timeout: set `DEV_RUN_TIMEOUT_MINUTES=1`, Resume, expect `awaiting_customer` + "Build exceeded the time limit" with logs, then restore.
9. **Delivery approval (customer)** - press Approve delivery: status → `finished`, customer notified by email.
10. **Report** - PASS/FAIL per step with evidence (status history, PR URL, demo HTTP code, mailpit subjects). Fix any bug found on its own branch with a pull request via `gh pr create` (never push to main). Restore every `.env` toggle you changed and leave the stack running.
